# [FEE-1011] Accessible Name 計算：AccName 演算法如何決定標籤

:::info
螢幕閱讀器公告一個控制項時，唸出的字串來自 W3C Accessible Name and Description Computation 規範定義的 accessible name 計算。演算法依固定順序檢查候選來源：aria-labelledby 最先，接著是 aria-label、host language 屬性、name from content，最後是 tooltip 屬性，第一個非空的結果勝出。Chrome DevTools 直接呈現這個計算：accessibility 面板依優先順序列出所有候選來源，並標出勝出者。誤讀這個優先順序會寫出真實的標籤 bug，例如一個 aria-label 把按鈕的可見文字整個蓋掉，輔助技術使用者從此聽不到那段文字。
:::

## Context

Accessible Name and Description Computation 1.2 是走 Recommendation 進程的 W3C Working Draft，最近一次發布是 2026 年 8 月 5 日，內容更新自 AccName 1.1 Recommendation。核心演算法歷經各版本仍維持同一形狀：一串固定順序的步驟，第一個非空結果勝出。規範把 host language 的細節交給 HTML Accessibility API Mappings（HTML-AAM），由它針對 `label`、`alt`、`placeholder`、`title` 等 HTML 元素調整 AccName 演算法。W3C ARIA Authoring Practices Guide 與各家無障礙廠商部落格的實務建議方向一致：優先用可見文字與原生 HTML 技巧，少用 ARIA 命名屬性。本 corpus 的 Accessibility 文章處處提到標籤；這一篇走完決定哪個標籤真正被公告的那套計算。

## Example

考慮一顆儲存按鈕，同時帶著三個相互競爭的名稱來源，外加一個 icon-font 字元：

```html
<style>
  .icon-save::before {
    font-family: "IconFont";
    content: "\f0c7";
  }
</style>

<button class="icon-save" title="Save the current draft" aria-label="Save">
  Save document
</button>
```

這裡沒有 `aria-labelledby`，演算法於是走到 aria-label 步驟並回傳它的值，算出的名稱是 `Save`。在 Chrome DevTools 選取這個元素並開啟 accessibility 面板：面板依計算優先順序列出候選來源，標出 `aria-label` 是勝出者，落選的候選排在下方。`aria-label` 在 button 上勝出，而 button 屬於支援以子內容命名的角色，所以可見文字 `Save document` 與 icon 字元對輔助技術使用者全數隱形。

刪掉 `aria-label` 之後，計算落到 name from content。這一步遞迴走訪子樹，規範要求 user agent 把 `::before` 的文字內容接在最前面、`::after` 的文字內容接在最後面。算出的名稱變成 private-use 字元 `\f0c7` 加上 `Save document`。按鈕裡的縮排與換行留不下來：結果會正規化成一條扁平字串，carriage return、換行、tab、form feed 一律變成單一空格，連續空格再合併成一個。

連 class 和可見文字也刪掉，只剩 `<button title="Save the current draft"></button>`。前面每個來源都空了，tooltip 步驟回傳 `title` 的值。實務建議把這個結果當成備援，不要當成刻意採用的命名技巧。

參照式命名的路徑對隱藏內容有不同的行為：

```html
<span id="discard-hint" style="display: none">Discard unsaved changes</span>
<button aria-labelledby="discard-hint">X</button>
```

隱藏節點通常只貢獻空字串給計算，但例外在這裡生效：這個 `span` 被 `aria-labelledby` 參照，內容照樣參與，按鈕公告成 `Discard unsaved changes`。可見的 `X` 落選，因為 `aria-labelledby` 在步驟順序裡排在 name from content 前面。

## Best Practices

- 禁止在角色禁止命名（name prohibited）的元素上使用 `aria-label` 或 `aria-labelledby`；規範定義這些角色沒有名稱。
- 在支援以子內容命名的角色上使用 `aria-label` 時，必須用輔助技術實測，因為對輔助技術使用者而言，屬性值會替換掉全部子孫內容，而且永遠不會渲染在畫面上。
- 應該用控制項的可見文字為它命名；ARIA Authoring Practices Guide 指出這樣做簡化維護、減少 bug，也降低翻譯需求。
- 應該優先用 `label`、`alt` 等原生 HTML 命名技巧，少用 ARIA 屬性；用錯的 ARIA 會蓋掉正確的 HTML 語義，ARIA 用得重的頁面錯誤率也更高。
- 不應該把 `title` 屬性當成主要命名手段；它只在沒有更強來源時才生效，APG 的基本原則也包含避開瀏覽器備援。
- 應該在 Chrome DevTools 的 accessibility 面板驗證算出的名稱，面板依計算優先順序列出候選來源並標出勝出者。
- 應該遵循 APG 的基本原則，把名稱寫得簡短、有用。
- 可以用 `aria-labelledby` 參照隱藏元素；隱藏節點的排除規則對被 `aria-labelledby` 或 `aria-describedby` 參照的節點不適用。

## Failure Modes

以下每個 bug 都對應到計算中的特定步驟，也都能在 DevTools accessibility 面板觀察到，面板會列出候選來源與勝出者。

**aria-label 讓可見文字消音。** aria-label 步驟排在 name from content 前面，所以在 button、link 這類以內容命名的角色上，`aria-label` 會替輔助技術使用者換掉元素裡的一切。一顆畫面上寫著 `Save document` 的按鈕，帶上 `aria-label="Submit"` 之後公告成 `Submit`。APG 提醒這種情況特別需要用輔助技術實測，因為 `aria-label` 的值永遠不會渲染在畫面上。

**display:none 的標籤照樣開口。** 隱藏節點在一般走訪時回傳空字串，開發者於是以為把元素藏起來就等於移出計算。但被 `aria-labelledby` 或 `aria-describedby` 參照的節點例外，`display: none` 的目標照樣貢獻文字。重構後遺留的過期隱藏 `span`，會一直蓋掉按鈕的可見文字。

**icon-font 字元污染名稱。** name from content 進行時，user agent 會把 `::before` 的文字內容接在前、`::after` 的接在後。透過 `content` 注入 private-use 字元的 icon font，會把那個字元加進它裝飾的每個元素的名稱，公告開頭因此多了一個唸不出來的字元。

**放在禁止命名角色上的名稱蒸發。** 對名稱被禁止的角色而言，元素沒有名稱，規範也禁止作者在這些角色上使用 `aria-label` 或 `aria-labelledby`。放上去的 `aria-label` 不會產生預期的公告。
