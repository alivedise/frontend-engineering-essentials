# TypeScript 總覽

TypeScript 是 JavaScript 的靜態型別超集合，編譯後產生純 JavaScript。每一個合法的 JavaScript 檔案都是合法的 TypeScript 檔案。TypeScript 加入了一套型別系統，該系統在編譯時期會被完全抹除——不會產生任何執行時期的額外負擔。編譯器會剝除所有型別標註，產生慣用的 JavaScript，可在任何 JavaScript 能運行的環境中執行：瀏覽器、Node.js、Deno、邊緣執行環境。

TypeScript 提供的核心價值，在於將一整類錯誤從執行時期提前至編譯時期發現。一個拼錯的屬性名稱、一個傳入錯誤引數型別的函式呼叫、一個對 null 的屬性存取——這些錯誤在 JavaScript 中只有在程式碼真正執行時才會被發現，往往是在正式環境中、針對特定使用者的特定程式碼路徑上，而這些路徑在測試時未必會被執行到。TypeScript 則在程式碼撰寫的當下就能發現這些錯誤，在編輯器中，在任何測試執行之前。

這個取捨是真實存在的。TypeScript 需要一個編譯步驟與 tsconfig 設定，增加了閱讀和撰寫的語法負擔，並在第三方函式庫未附帶型別宣告時，產生維護型別宣告的義務。問題不在於 TypeScript 是否優秀，而在於專案的脈絡——團隊規模、程式碼庫的生命週期、複雜度——是否足以證明這些額外負擔是值得的。對於大多數打算維護超過幾個月的專案的團隊來說，答案是肯定的。模組之間的溝通誤差、能被型別檢查攔截的執行時期錯誤，其累積速度往往超過維護型別的成本。

本文是 TypeScript 分類的總覽：每篇文章涵蓋型別系統的一個面向或一個應用層面的關切點。章節順序——基礎概念、泛型、工具型別、型別縮窄、型別宣告、設定、React 整合、執行時期驗證——反映了開發者在將 TypeScript 導入實際專案時會依序遭遇這些主題的順序。

## 設計思維

### TypeScript 的型別系統是結構性的，而非名義性的

TypeScript 採用結構性型別系統：兩個型別是否相容，取決於它們的形狀是否相同，而與名稱無關。一個預期接收 `{ name: string }` 的函式，會接受任何具有 `name` 字串屬性的物件——它不要求該物件是由某個特定具名型別所宣告的。這與 Java 或 C# 等語言的名義性型別系統不同；在名義性型別系統中，型別相容性由明確的繼承或介面實作決定，而非由形狀決定。

實際的影響是：TypeScript 的介面和型別別名描述的是資料的形狀，任何滿足該形狀的值都滿足該型別。這使得 TypeScript 與 JavaScript 的鴨子型別風格自然相容：沒有型別的程式碼，通常可以用一個符合其形狀的型別來描述，而不需要更動程式碼本身。這也意味著兩個獨立定義但形狀相同的介面是可以互換的——不需要明確的 `implements` 宣告來使其相容。

這種結構性方式有其限制。當兩個形狀意外地相容——例如 `UserId` 和 `OrderId` 都是 `string` ——TypeScript 無法捕捉兩者之間的混用錯誤，除非讓型別在結構上有所區別（使用品牌型別或不透明型別）。習慣名義性型別語言的開發者，有時會期望型別名稱能提供安全保障，但這種安全保障只有在結構上有所不同時才能實現。

### 採用 TypeScript 的成本隨延遲而增加

將 TypeScript 補加到現有 JavaScript 程式碼庫需要逐一修改每一個檔案。每個檔案都需要加入型別標註並解決型別錯誤，TypeScript 才能接受它。等到程式碼庫已經龐大才開始導入的團隊，面對的是一場需要數週的遷移工程，過程中必須使用 `any` 標註作為逃脫出口來快速讓建置通過，而這些逃脫出口在遷移名義上完成後往往仍然存在——在持續開發的壓力下，它們常常永遠不會被清除，留下型別覆蓋率上的靜默漏洞。

從一開始就採用 TypeScript 的成本只需一個下午的設定時間。一個新專案需要一個 `tsconfig.json`、在建置流程中加入一個編譯步驟，以及決定是直接使用 TypeScript 檔案（透過 ts-node、tsx 或能處理 TypeScript 的打包工具），還是編譯至獨立的輸出目錄。這個設定是穩定的，不需要隨著專案成長而改變。每一個新增的檔案從一開始就是有型別的；永遠不需要進行補加遷移。

遷移成本並非線性增長。一個 10 個檔案的 JavaScript 專案可以在一天內遷移至 TypeScript。300 個檔案的專案需要數週。1,000 個檔案的專案可能需要一個正式的遷移專案與專屬資源。TypeScript 的導入被拖延得越久，遷移成本相對於效益的比例就越高。

### TypeScript 不能取代執行時期驗證

TypeScript 的型別在編譯時期會被完全抹除。編譯後的 JavaScript 不包含任何型別資訊——沒有檢查、沒有斷言、沒有守衛。一個被標註為 `User` 型別的 API 回應，在執行時期並不會被驗證為 `User`；它只是被信任為 `User`。如果 API 在預期 `User` 的地方回傳了 `null`，TypeScript 無法捕捉這個錯誤。型別標註表達的是開發者的預期；它並不強制執行這個預期。

來自外部來源的資料——API 回應、localStorage 的值、URL 參數、表單輸入、環境變數——必須在執行時期透過結構描述函式庫進行驗證。Zod、Valibot 等函式庫提供了一種機制，能解析無型別的資料，並在資料符合預期形狀時產生一個有型別的結果，或在不符合時拋出具描述性的錯誤。結構描述同時作為執行時期的驗證器和 TypeScript 型別的來源；兩者不會不同步，因為型別是從結構描述衍生出來的。

這個區別是 TypeScript 導入過程中最常見的誤解之一。期望 TypeScript 能防止由意外的 API 形狀或格式錯誤的輸入所造成的執行時期錯誤的開發者，會在這些錯誤發生時感到困惑。TypeScript 防範的是開發者撰寫的程式碼中的錯誤；它無法防範程式碼所接收的資料造成的錯誤。這個區別在 FEE-1708 中有深入的討論。

## 最佳實踐

**必須（MUST）在新專案一開始就加入 TypeScript，而非等到程式碼庫成長後再補加。** 補加 TypeScript 需要逐一修改每個檔案以加入型別標註並解決錯誤。等到程式碼庫已龐大才延遲導入的團隊，面對的是一場需要數週的遷移工程，過程中必須使用 `any` 標註作為逃脫出口——這些標註在遷移名義上完成後往往仍然存在，留下型別覆蓋率上的靜默漏洞。在專案起始時導入 TypeScript 的設定成本很低；遷移成本則與程式碼庫規模成正比增長。

**必須（MUST）在專案初始化時於 `tsconfig.json` 中啟用 `strict` 旗標。** 嚴格模式會同時啟用 `noImplicitAny`、`strictNullChecks`、`strictFunctionTypes`、`strictBindCallApply`、`strictPropertyInitialization` 等多項檢查——完整清單請參閱 [tsconfig 參考文件](https://www.typescriptlang.org/tsconfig#strict)。解決嚴格模式錯誤的成本在程式碼庫較小時最低。在程式碼庫成長後才啟用嚴格模式，需要修復數百個既有錯誤，並導致長期的建置失敗狀態。在沒有使用 `strict` 總旗標的情況下單獨啟用各個嚴格旗標，也可能錯過未來 TypeScript 版本中新增的嚴格檢查項目。

**禁止（MUST NOT）在沒有說明原因與可移除時機的情況下使用 `@ts-ignore`。** 一個裸露的 `@ts-ignore` 會壓制型別錯誤，並移除所有關於原因的紀錄。當根本問題在上游被解決——函式庫附上了自己的型別、結構上的變更使型別轉換變得不必要——這個指令仍會無限期地保留，無聲地擴大型別安全的缺口。每一個壓制指令都是技術債；以此態度對待它，就意味著必須加以記錄。

**應該（SHOULD）以生產環境中與型別相關的執行時期錯誤率來衡量 TypeScript 採用品質，而非型別覆蓋率。** 型別覆蓋率工具衡量的是程式碼庫中有多少部分具有明確的型別標註，但一個具有 95% 覆蓋率卻大量使用 `any` 的程式碼庫，其型別安全性可能比一個 80% 覆蓋率但啟用嚴格模式的程式碼庫更差。由「屬性不存在」或「無法讀取 undefined 的屬性」所引發的生產環境錯誤率，才是 TypeScript 本應消除的訊號。
