# 型別收窄與型別守衛

型別收窄是 TypeScript 在條件分支內精煉值的型別的機制。當程式碼檢查 `typeof value === 'string'` 時，TypeScript 知道在 true 分支內，`value` 是 `string`。這種檢查——以及使用 `instanceof`、`in` 運算子、相等比較和真值性的類似檢查——被稱為型別守衛。TypeScript 無需明確註解即可理解它們，並自動進行收窄。

實際的結果是，在撰寫良好的 TypeScript 中，大多數收窄不需要自訂程式碼——內建守衛涵蓋了常見情況。使用述詞語法（`value is T`）的自訂型別守衛填補了剩餘的缺口：當收窄條件複雜到需要提取到函式中時，述詞回傳型別告訴 TypeScript 該函式的真值回傳會收窄參數。

辨別聯合是最強大的收窄模式，因為它們將型別安全與完整性檢查結合在一起：每個成員都有字面 `type` 欄位的聯合可以被 switch 處理，TypeScript 將每個分支收窄到特定成員。在不更新所有 switch 語句的情況下新增聯合成員將成為編譯錯誤，而非無聲的執行時回落。

## Design Thinking

### 內建收窄：常見情況

`typeof` 收窄基本型別；`instanceof` 收窄類別實例；`in` 收窄具有特定屬性的物件；真值性收窄掉 `null | undefined`；相等比較（`=== 'value'`）收窄到字面型別。TypeScript 透過控制流程追蹤收窄，包括跨賦值、迴圈和提前回傳。

### 辨別聯合：最強大的模式

每個成員都具有唯一值的字面 `type` 或 `kind` 欄位的聯合是辨別聯合。對 `type` 進行 switch 可將每個分支收窄到特定成員。這比 `instanceof` 鏈更具可讀性和可維護性，且成員是可以一致地序列化、反序列化和模式匹配的純物件。

### 何時需要自訂型別守衛

當收窄條件複雜到需要提取到輔助函式中時，回傳型別 `value is T` 告訴 TypeScript `true` 回傳意味著參數是 `T`。若沒有述詞語法，提取的函式回傳 `boolean`，收窄在呼叫點丟失——程式碼正確執行，但 TypeScript 不再知道真值分支中已收窄的型別。

## 最佳實踐

**必須（MUST）對加總型別使用帶有字面 `type` 或 `kind` 欄位的辨別聯合，而非可選欄位或 `instanceof` 檢查。** 辨別聯合啟用完整性檢查，在 switch 語句中無需自訂守衛即可產生乾淨的收窄，並且可以在不帶原型資訊的情況下進行序列化。可選欄位會產生模糊的收窄——欄位的存在並不能表明值代表哪個變體。`instanceof` 與建構子產生耦合，並在序列化邊界中失效。

**必須（MUST）將型別述詞（`value is T`）作為自訂守衛函式的回傳型別，而非回傳 `boolean`。** 回傳 `boolean` 的守衛函式不會將收窄傳播到呼叫點——TypeScript 只看到一個布林值，而非收窄斷言。述詞語法 `function isUser(value: unknown): value is User` 告訴 TypeScript `true` 回傳意味著參數滿足 `User` 型別，收窄在每個呼叫點的真值分支中都能正確流動。

**應該（SHOULD）優先使用 `in` 運算子收窄和辨別聯合，而非對純資料物件使用 `instanceof` 收窄。** `instanceof` 與特定建構子函式產生耦合，在兩個相同類別實例具有不同建構子參照的 iframe 邊界中失效，且對 JSON 反序列化建立的物件無效，因為 JSON 物件從不攜帶類別原型。辨別聯合和 `in` 收窄對任何來源的純物件都有效。

**應該（SHOULD）使用斷言函式（`asserts condition`）來編碼在程式碼特定位置必須成立的前置條件。** 對假值條件拋出例外的斷言函式告訴 TypeScript，在呼叫之後，條件被收窄為 true。這對於守衛初始化值以及表達 TypeScript 無法從控制流程推斷的不變量非常有用——例如，在需要某個選用欄位的程式碼區段之前，斷言該欄位已被填入。
