# 型別系統基礎與型別推論

TypeScript 的型別系統有兩種運作模式：明確的型別標註（開發者直接指定型別）和型別推論（TypeScript 從值或上下文中推導型別）。大多數情況下，推論已經足夠，標註反而是雜訊。理解各自適用的場合，是學習 TypeScript 的第一個實用技能。

基本型別（`string`、`number`、`boolean`、`null`、`undefined`、`symbol`、`bigint`）以及逃生出口（`any`、`unknown`、`never`）構成了型別系統的基礎。`any` 會停用型別檢查。`unknown` 是安全的替代方案——它接受任何值，但在使用前強制進行型別收窄。`never` 代表不可到達的程式碼，並驅動窮舉性檢查。

聯合型別（`string | number`）和交集型別（`A & B`）讓型別系統能夠表達「其中之一」和「全部皆是」。字面型別（`'success' | 'error'`）將字串、數字、布林值轉化為型別，進而實現辨別聯合與窮舉性檢查。

## 設計思維

### 推論消除多餘的型別標註

TypeScript 會將 `const x = 42` 推論為 `number`、將 `const arr = [1, 2, 3]` 推論為 `number[]`，並從回傳運算式推論函式的回傳型別。手動標註這些型別只會增加維護負擔，卻不帶來額外的安全保障。需要明確標註的邊界在於：函式參數（推論無法跨越呼叫點）、公開 API 的回傳型別（明確的合約），以及先宣告後賦值的變數。

### any 與 unknown 的差異至關重要

`any` 是雙向的逃生出口：型別為 `any` 的值可以被賦值給任何型別，也可以對其執行任何操作而不產生錯誤。`unknown` 則是單向的：任何值都可以賦值給 `unknown`，但 `unknown` 在收窄之前無法被使用。這使得 `unknown` 適合用來表示真正未知的輸入（JSON 回應、錯誤的 catch 子句），而 `any` 則不適合任何情境。

### never 作為正確性證明

一個永遠拋出例外的函式，其回傳型別為 `never`。一個處理了聯合型別所有成員的 switch 陳述式，其 default 分支是不可到達的——TypeScript 會將該分支的型別標記為 `never`。若將該值賦值給一個型別為 `never` 的變數，當新的聯合成員被加入而 switch 未更新時，就會產生編譯錯誤。這個模式稱為窮舉性檢查。

## 最佳實踐

**必須（MUST）優先使用 `unknown` 而非 `any` 來表示真正未知的型別。** `any` 會停用對該值及其衍生值的所有型別檢查——對 `any` 值進行屬性存取會回傳 `any`，導致不安全性在程式碼庫中無聲蔓延。`unknown` 在使用前強制進行明確的型別收窄，保留了型別安全的保證。在錯誤的 catch 子句、反序列化的 JSON，以及任何在呼叫點不知道形狀的值中，都應使用 `unknown`。

**必須（MUST）在 switch 陳述式和辨別聯合處理器中使用 `never` 窮舉性檢查。** 當 switch 陳述式處理辨別聯合時，default 分支應將值賦值給一個型別為 `never` 的變數。若新成員被加入聯合而 switch 未更新，賦值將無法編譯。這個模式讓 switch 成為編譯期的合約：新增變體而不處理它，會是建置錯誤，而非靜默的執行時跳過。

**應該（SHOULD）讓 TypeScript 自動推論區域變數、陣列/物件字面值，以及回傳值型別明確的函式回傳型別。** 在可推論的位置加上明確標註，會增加程式碼雜訊並形成第二個真相來源，可能與實際型別產生偏差。明確標註應保留給函式參數、公開 API 的回傳型別，以及先宣告後賦值的變數。

**應該（SHOULD）使用字面型別和聯合型別來模型化領域值，而非將其擴展為 `string` 或 `number`。** 一個型別為 `'pending' | 'fulfilled' | 'rejected'` 的狀態欄位，比 `string` 更精確，且能在對該欄位進行 switch 的任何地方啟用窮舉性檢查。擴展為 `string` 會丟棄約束，並移除所有狀態都被處理的編譯期保證。
