# 泛型

泛型讓函式、介面或類別能夠操作在呼叫端決定的型別，而非在定義時就固定下來。一個將值包裝成陣列的函式，可以對任何型別正確運作，且不會像使用 `any` 的非泛型版本那樣，遺失型別資訊。

泛型的威力在於型別傳遞：輸入型別與輸出型別之間的關係得以保留。一個回傳 `T[]` 陣列第一個元素的函式，其回傳型別是 `T`，而非 `unknown`。呼叫端無需型別斷言，就能知道自己會收到什麼型別。

泛型經常被過度使用。一個型別參數若只出現一次——只用於輸入而未出現在其他地方——只會增加複雜度，並不帶來任何好處。型別約束是限制型別參數範圍的機制：`<T extends string>` 將 T 限制為字串的子型別；`<T extends { id: number }>` 則將 T 限制為含有 `id` 欄位的物件。

## 設計思維

### 泛型在操作中保留型別資訊

一個接受 `any` 並回傳 `any` 的非泛型 identity 函式會遺失型別：呼叫端無法得知回傳值與傳入引數的型別相同。泛型版本 `<T>(value: T): T` 則保留了這個關係——回傳型別與輸入型別相同，TypeScript 會在呼叫端進行推論，無需任何斷言。泛型版本讓呼叫端對回傳值的後續操作都能取得正確的型別資訊。

### 約束表達最低要求的形狀

一個存取 `value.length` 的泛型函式，可以使用 `<T extends { length: number }>` 而非 `<T extends string | Array<any>>`。這對意圖的描述更為精確——該函式要求任何具有 length 屬性的值——而對能力的描述更為寬泛：它接受具型別的陣列、字串，以及任何帶有 length 欄位的自訂物件。約束應當表達函式主體實際需要的最低結構要求，而非列舉出作者預期呼叫端會傳入的所有型別。

### 何時不應使用泛型

一個接受 `string | number` 並回傳 `string | number` 的函式，使用泛型並不能帶來任何好處。泛型版本 `<T extends string | number>(value: T): T` 更難閱讀，也不會提供額外的型別安全。當輸入與輸出的關係是對稱的，使用聯集型別；當輸出型別需從特定的輸入型別推導時，才使用泛型。有疑慮時，先寫聯集型別——如果呼叫端需要輸出型別精確縮窄為輸入型別，那才是引入泛型的訊號。

## 最佳實踐

**必須（MUST）在函式主體存取參數的屬性或方法時，為泛型型別參數加上約束。** 當函式存取 `value.id` 時，使用 `<T extends { id: string }>` 而非裸露的 `<T>`，可以明確表達需求、在違反約束時提供更清楚的錯誤訊息，並防止呼叫端傳入執行時期會失敗的不相容型別。

**禁止（MUST NOT）定義在整個簽名中只出現一次的泛型型別參數。** 只出現一次的型別參數無法從呼叫端引數推論，每次呼叫都需要明確標注。如果呼叫端每次都必須寫 `fn<string>(arg)` 而非 `fn(arg)`，泛型提供的不是推論，而是強制標注。使用較簡單的多載或聯集型別會更清晰。

**應該（SHOULD）只在型別參數真正可與任何型別互換時使用單字母命名。** `T` 適用於泛型 identity 函式。當型別參數具有語意意義——代表資源型別、鍵型別或實體——應使用有意義的名稱：`ResourceType`、`KeyType`、`EntityShape`。有意義的名稱讓複雜的泛型簽名在不需文件說明的情況下也能閱讀。

**應該（SHOULD）在條件型別中使用 `infer` 來提取複合型別中的元件型別，而非要求呼叫端明確提供型別引數。** `ReturnType<typeof fn>` 使用 `infer` 從函式型別中提取回傳型別，無需呼叫端標注。當工具型別需要深入另一個型別以提取其中一部分時，在條件型別中使用 `infer R` 是正確的做法。
