# 工具型別與型別操作

TypeScript 內建一套泛型工具型別，可將現有型別轉換為新型別。這些工具型別 — `Partial`、`Required`、`Readonly`、`Pick`、`Omit`、`Exclude`、`Extract`、`ReturnType`、`Parameters`、`NonNullable`、`Record` — 讓開發者在需要型別變體時，無須手動重新定義型別形狀。手動重新定義的型別形狀會在來源型別變動時悄然失去同步；結構性衍生則會自動保持一致。

最常用的工具型別分為兩組：形狀轉換器（`Partial`、`Required`、`Readonly`、`Pick`、`Omit`）產生物件型別的修改版本，以及函式型別提取器（`ReturnType`、`Parameters`）從函式簽名衍生型別。兩組工具型別都能消除 TypeScript 型別系統與其所描述的程式碼之間的重複。

所有內建工具型別都是以映射型別實作的 — 這個模式同樣適用於應用程式程式碼。當沒有任何內建工具型別能表達所需的轉換時，使用 `{ [K in keyof T]: ... }` 的自訂映射型別即可填補這個缺口。

## 設計思考

### 衍生與重複定義

重複定義另一個型別部分欄位的型別，會在來源型別演進時悄然失去同步。`Pick<User, 'id' | 'name'>` 會自動反映 `User` 的 `id` 和 `name` 欄位的任何變更。重複定義製造了一個沒有任何強制機制的維護義務；結構性衍生則是自我更新的。

### 映射型別：工具型別的引擎

`Partial<T>` 和 `Readonly<T>` 等內建工具型別都是以映射型別實作的：`{ [K in keyof T]?: T[K] }` 和 `{ readonly [K in keyof T]: T[K] }`。理解這個模式，讓開發者在內建工具型別不符需求時，能夠自行撰寫自訂工具型別。

### 字串操作的樣板字面型別

TypeScript 4.1+ 支援樣板字面型別，以及字串轉換工具型別 `Uppercase<S>`、`Lowercase<S>`、`Capitalize<S>`、`Uncapitalize<S>`。這些型別讓型別層級的字串操作成為可能，適用於事件名稱衍生、CSS 屬性鍵生成以及 API 鍵命名慣例等使用情境。

## 最佳實踐

**必須（MUST）在需要現有型別的子集或排除版本時，使用 `Pick<T, K>` 和 `Omit<T, K>`，而非手動重新定義型別形狀。** 手動重新定義會製造第二個事實來源，當來源型別新增、移除或重新命名欄位時，這份副本會悄然偏離。以 `Pick` 和 `Omit` 進行結構性衍生是一種意圖宣告 — 「這個型別是那個型別的這個子集」— TypeScript 會自動加以強制。

**必須（MUST）對作為設定傳入、儲存為模組層級常數或用作預設值的物件使用 `Readonly<T>`。** `Readonly<T>` 在呼叫端防止意外的變動，且沒有任何執行期開銷 — 檢查僅在編譯期進行。對於淺層 readonly 不足的深層巢狀物件，在字面值上使用 `as const`，可產生深度 readonly 的型別。

**應該（SHOULD）使用 `ReturnType<typeof fn>` 和 `Parameters<typeof fn>` 從現有函式簽名衍生型別，而非重複定義。** 當函式簽名變更時，從 `ReturnType` 和 `Parameters` 衍生的型別會自動更新。另行維護的型別宣告則需要人工更新，並依賴開發者主動察覺不一致。

**應該（SHOULD）在內建工具型別無法表達所需轉換時，自行建立映射型別。** `{ [K in keyof T]: ... }` 這個模式是所有內建工具型別的基礎，同樣適用於應用程式程式碼。將每個值包裝成 `Promise` 的自訂映射型別 — 產生物件介面的非同步版本 — 是慣用的 TypeScript 寫法，而非只有函式庫作者才能使用的進階技巧。
