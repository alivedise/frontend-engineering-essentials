# 元件層級的記憶化

React 的渲染模型會在父元件重新渲染、元件本身的狀態改變，或其所消費的 context 發生變更時，觸發
元件重新渲染。對大多數元件而言，這是正確且快速的行為。但對於渲染成本較高的元件——大型列表、複雜
的 canvas 操作、沉重的運算——不必要的重新渲染會累積成使用者可感知的延遲。記憶化 API
（`React.memo`、`useMemo`、`useCallback`）讓元件與值在輸入未發生變化時，得以跳過重新計算。
React 的渲染模型設計為盡可能快且正確，記憶化是在特定瓶頸點有針對性地介入，而非對渲染模型的
全面覆寫。掌握三個 API 各自的適用邊界，是從「加上去不知道有沒有用」演進到「有憑有據的效能最佳
化」的關鍵一步。

React 團隊的建議是在效能分析之後才應用記憶化，而非預先套用。記憶化本身有成本：每次渲染時都需要
比對先前與當前的 props 或依賴項。對於渲染成本低的元件，比對成本反而超過它所避免的渲染成本。對
每個元件都套用 `React.memo` 並不是最佳化——這只是製造噪音，讓程式碼更難閱讀，在整體上甚至可能
讓效能更差。不以量測問題為基礎的最佳化是猜測，而猜測日積月累，會讓程式碼庫演變成沒有人能自信
地推理的狀態。

理解記憶化的隱性成本，有助於建立正確的應用直覺。每一個 `useMemo` 和 `useCallback` 的調用都引入
了一個必須保持準確的依賴陣列：當元件的 props 或邏輯演進時，依賴陣列也必須同步更新，否則會產生
難以追蹤的過時閉包錯誤。記憶化越多，重構時需要維護的心智負擔就越重。這不是反對使用記憶化的理由，
而是強調：記憶化應該服務於可量測的效能問題，而非成為防禦性程式設計的慣用手法。

記憶化的正確心智模型是打破重新渲染鏈：`React.memo` 阻止元件在父元件重新渲染且 props 未改變
時重新渲染；`useMemo` 阻止元件在重新渲染時，依賴項未改變的值被重新計算；`useCallback` 阻止
元件在重新渲染時，依賴項未改變的函式被重新建立。三者都依賴參考穩定性運作——只有在消費者關心
參考相等性時才有幫助。參考穩定性對 `React.memo` 包裹的子元件（props 比對）以及將某個值列為
依賴項的 hook 而言至關重要；對只在當前元件本身的渲染輸出中使用的值則無關緊要。

將這三個 API 視為一個協調系統而非各自獨立的工具，是正確應用它們的關鍵。對子元件套用
`React.memo` 只有在傳遞給它的 props 本身也是穩定的情況下才有成效，這通常需要父元件對任何作為
物件、陣列或函式的 prop 使用 `useMemo` 或 `useCallback`。三個 API 在一起作為鏈使用時最為有效，
而非零散地分布於程式碼庫中。

## 設計思維

### 記憶化本身的成本

一個常見的誤解是，當記憶化避免了一次渲染時，它的代價是免費的。實際上，記憶化在每次渲染時
都有固定的成本：比對先前與當前的依賴項（對 `useMemo` 和 `useCallback`）或 props（對
`React.memo`）。對 `useMemo` 和 `useCallback`，此成本與依賴陣列中的項目數量成正比。對
`React.memo`，成本與 props 的數量成正比。當被記憶化的元件渲染成本很低——一個只回傳幾個 DOM
節點的簡單片段——每次渲染時的比對成本，可能超過記憶化所避免的渲染成本。

這種不對稱性正是 React 團隊建議在效能分析之後才套用記憶化的原因。一個很少渲染的記憶化元件，
仍然在每次父元件渲染時支付比對成本。如果父元件每秒渲染數千次——例如在動畫幀循環中——且記憶化
的子元件渲染很廉價，比對的額外負擔會累積而不產生相應的收益。效能分析必須顯示子元件的渲染本身
是瓶頸，而非父元件頻繁渲染，才能確認記憶化值得引入。

這個原則同樣適用於 `useMemo`：如果被記憶化的計算在每次渲染中只需要零點幾毫秒，那麼記憶化所帶
來的認知複雜度（維護依賴陣列、理解閉包邊界）和固定比對成本，往往超過其帶來的實際收益。以
`console.time` 基準測試計算，是在決定記憶化之前的快速驗證手段。

### React.memo 真正發揮作用的時機

`React.memo` 阻止元件在父元件重新渲染且子元件的 props 參考未改變時重新渲染。若要使其帶來淨
收益，以下三個條件必須同時為真：父元件頻繁重新渲染、子元件的 props 在這些父元件重新渲染間保持
穩定，以及子元件的渲染成本夠高，跳過渲染能節省可量測的時間。在大多數元件樹中，至少有一個條件
為假。只在使用者互動時才重新渲染的父元件，其重新渲染頻率低，子元件的重新渲染並非瓶頸；每次父
元件渲染都接收到新物件字面值作為 prop 的子元件，其 props 不穩定，`React.memo` 執行比對後仍會
重新渲染；只回傳小型片段的子元件，渲染如此低廉，節省其渲染時間是無法觀察到的。

在新增 `React.memo` 之前的實務測試是：開啟 Profiler，錄製感覺緩慢的互動，查看目標元件是否
顯示為長條（代表耗時較長的渲染）。若該元件未出現為慢速元件，`React.memo` 無濟於事。若出現了，
再檢查其 props 是否確實穩定——透過 Profiler 的「為何重新渲染？」標註查看哪些 props 發生了
變化。唯有兩個條件都由量測確認後，`React.memo` 才有正當性。

一個細微但重要的要點是，`React.memo` 使用 Object.is 語義進行比對，對物件與陣列執行的是淺層
參考比對。兩個包含相同項目但為不同陣列實例的陣列，比對結果為不相等。這意味著若父元件以行內方式
傳遞一個計算得出的列表——例如在 JSX 中寫 `items.filter(predicate)`——`React.memo` 在每次父元件
渲染時都會看到新的陣列參考，並無條件重新渲染子元件。父元件必須先以 `useMemo` 穩定陣列參考，
`React.memo` 才有機會中止渲染。忽略這個 `React.memo` 與不穩定 prop 參考之間的交互作用，是開發
者加上 `React.memo` 後卻在 Profiler 中觀察不到任何改善的最常見原因之一。

另一個值得了解的 `React.memo` 進階用法是自定義比對函式。`React.memo` 接受第二個可選引數，一個
接受 `prevProps` 和 `nextProps` 的比對函式，若回傳 `true` 則跳過重新渲染，回傳 `false` 則
重新渲染。這在預設淺層比對產生過多偽陽性的情境下有用——例如，一個接受包含大型巢狀物件的 prop，
但只關心其中某一個欄位的子元件。然而，自定義比對函式本身就是一個高維護性的抽象，容易在 props
結構改變時變得不正確。在大多數情況下，重新設計 prop 結構使其適合淺層比對，優先於引入自定義比對
函式的複雜度。

### useMemo 用於高成本的計算

`useMemo` 對計算值進行記憶化，並在列出的依賴項未改變的情況下，跨渲染重複使用該值。它真正有幫
助的使用情境包括：對大型列表進行篩選或排序、從陣列建立查找映射或索引、執行佈局或幾何計算，或
建立供多個子元件消費的衍生資料集。這些情境的共同特徵是：計算在相同輸入下必然產生相同輸出，且
輸入的變更頻率遠低於元件重新渲染的頻率，使得快取上一次結果能夠帶來可觀的節省。

關鍵的限定條件是「高成本」。大多數針對千筆以下項目的陣列操作在一毫秒內完成，低於可感知延遲的
門檻。對一個十項篩選加上 `useMemo`，徒增依賴陣列的求值、記憶化快取查找的開銷，以及認知複雜
度——對使用者毫無可見的收益。一個簡單的啟發式方法是在記憶化之前以 `console.time` 對計算進行
基準測試：若它在一毫秒以內穩定完成，`useMemo` 開銷的成本與維護依賴陣列的負擔，不太可能是值
得的。

`useMemo` 的次要有效使用情境，是產生一個穩定的物件參考以作為 prop 傳遞給 `React.memo` 包裹的
子元件。在這種情況下，計算本身可能並不昂貴，但目標是參考穩定性，而非跳過昂貴的計算。這是對
低成本計算使用 `useMemo` 仍站得住腳的唯一情境——但仍然需要子元件確實被 `React.memo` 包裹，且
重新渲染已被量測為問題所在。在決定使用 `useMemo` 之前，問自己：「若移除這個 `useMemo`，使用者
會注意到差異嗎？」若答案是否定的，保持程式碼的簡潔通常優先於記憶化帶來的邊際收益。

### useCallback 與參考穩定性

`useCallback(fn, deps)` 回傳一個記憶化的函式參考，只要列出的依賴項未改變，該參考在渲染間保持
穩定。其目的純粹是參考穩定性，而非跳過昂貴的工作。它帶來淨收益的兩個情境是：將函式作為 prop
傳遞給 `React.memo` 包裹的子元件（此時父元件每次渲染產生的新函式參考會使 memo 失效）；以及將
函式列為另一個 hook（如 `useEffect`）的依賴項（此時每次渲染的新函式參考會導致 effect 在每次
渲染時執行）。

值得注意的是，當一個函式被設計為同時作為事件處理器和 `useEffect` 的依賴項時，`useCallback` 就
有了正當性，因為後者構成了第二個情境的需求。常見的例子是一個「載入資料」函式，既作為按鈕的
`onClick` 處理器，也被 `useEffect` 在元件掛載時自動呼叫。若不用 `useCallback` 使其穩定，每次
渲染都產生新的函式參考，`useEffect` 會在每次渲染後重新執行，觸發無限載入迴圈。在這個情境中，
`useCallback` 不是可選的最佳化，而是確保 effect 行為正確的必要條件。

在這兩個情境之外，`useCallback` 不帶來任何收益。只在元件本身的事件處理器中使用的函式——未向下
傳遞、未列為依賴項——雖然在每次渲染時重新建立，但這不會造成任何影響，因為 `React.memo` 與任何
hook 都沒有監看其參考。將這樣的函式包裹在 `useCallback` 中，只是增加了需要維護的依賴陣列，並
為審閱者增加一層思維負擔，卻毫無執行期的收益。

一個有助於理解的等價關係是：`useCallback(fn, deps)` 在語義上等同於 `useMemo(() => fn, deps)`。
區別在於可讀性——`useCallback` 傳達了記憶化的值是函式這一意圖。掌握這個等價關係，有助於在推理
應使用哪個 hook 及其原因時更加清晰，也說明了兩個 hook 的依賴規則為何完全相同：兩者都儲存第一
個引數的結果，並在每次渲染時比對依賴陣列，以決定是回傳已儲存的結果還是重新執行計算。

### React Compiler 與自動記憶化

React 19 包含 React Compiler，這是一個建置時期的轉換工具，能根據輸入的靜態分析，自動對元件和
hook 應用記憶化。當 React Compiler 啟用時，它會生成等同於開發者手動撰寫 `React.memo`、
`useMemo` 和 `useCallback` 的程式碼——但這些程式碼來自對程式碼實際資料流的推導，而非手動維護的
依賴陣列。這消除了最常見的一類記憶化錯誤：不正確或不完整的依賴陣列。

在使用 React Compiler 的專案中，手動撰寫 `useMemo` 和 `useCallback` 在很大程度上變得不再必要。
編譯器自動處理常見情況，手動記憶化仍有意義的場景更加狹窄：編譯器的靜態分析無法推斷為高成本的
計算，或開發者希望以顯式方式表達意圖作為文件說明。`use no memo` 指令允許將特定函式從
編譯器管理的記憶化中排除，以應對自動行為不正確的情況。採用 React 19 的團隊應該（SHOULD）評估
是否能為其程式碼庫啟用 React Compiler，因為它從根本上解決了大多數記憶化相關錯誤，同時減少了
工程師必須撰寫和維護的標記程式碼量。

理解 React Compiler 的一個重要前提是：它不改變 React 的渲染模型，只是自動化了開發者本來需要
手動表達的記憶化意圖。編譯器無法神奇地讓渲染成本高的元件變得便宜——它只能確保當輸入未改變時，
已知昂貴的渲染不會被不必要地觸發。效能問題的根本原因若在於演算法複雜度或 DOM 更新的成本，記憶
化（無論是手動還是編譯器自動）都無法解決；必須回到演算法層面或渲染架構層面尋求改善。這個認知
確立了記憶化在效能最佳化工具箱中的正確定位：它是針對不必要重新渲染的有效工具，但不是效能問題
的萬能解法。

## 最佳實踐

**必須（MUST）啟用 `react-hooks/exhaustive-deps` ESLint 規則，並將其所有警告視為錯誤。**
`useMemo` 或 `useCallback` 中不完整的依賴陣列，會產生一個從先前渲染讀取過時值的過時閉包。這
是記憶化所引入的最常見的隱性、難以重現的錯誤來源。症狀是元件顯示或計算基於 hook 首次執行時
當下的值，但這些值此後已改變——因為依賴項被遺漏，hook 從未重新執行以取得更新後的值。lint 規則
在問題到達生產環境之前就能靜態偵測到它。以 `// eslint-disable-next-line` 抑制規則來讓過時閉包
「成為刻意行為」的做法，必須（MUST）附上說明遺漏原因的注解；在絕大多數情況下，正確的修正是
納入該依賴項，而非抑制警告。若納入依賴項後導致 hook 執行過於頻繁，問題通常在於依賴項本身不穩定，
應先解決依賴項的穩定性，而非繞過 lint 規則。常見的解決方式是將不穩定的物件或陣列用 `useMemo`
包裹，或將不穩定的函式用 `useCallback` 包裹，使其成為穩定的參考，再列入依賴陣列。

**應該（SHOULD）在應用 `React.memo`、`useMemo` 或 `useCallback` 之前，先使用 React DevTools
Profiler 量測渲染效能。** 不以量測問題為基礎的記憶化，只是在沒有驗證收益的情況下增加了複雜度。
Profiler 的火焰圖顯示每次互動中哪些元件重新渲染、每次渲染耗費多長時間，以及哪個 prop 或狀態
改變引發了重新渲染。這份資料區分了真正的瓶頸——某個在每次按鍵時觸發且耗時 20ms 的元件——與偽
陽性——某個重新渲染但在 0.5ms 以內完成的元件。應該（SHOULD）在新增記憶化之前記錄量測基準，
並在套用後再次量測，以便能夠評估最佳化效果，並在未達到預期改善時予以撤回。建立「量測 → 應用
→ 再量測」的三步驟習慣，不僅使最佳化決策有憑有據，也讓日後重構時能自信地移除不再必要的記憶化，
而不必擔心未知的效能退化，因為原始的量測基準提供了可比較的參照點。

**禁止（MUST NOT）對未傳遞給 `React.memo` 包裹元件或未列為其他 hook 依賴項的函式使用
`useCallback`。** 只用在當前元件本身事件處理器中的函式，其 `useCallback` 沒有任何收益；無論
函式參考是否穩定，元件都會重新渲染，因為沒有任何外部消費者監看這個參考。在此情境下，
`useCallback` 是有成本（需維護的依賴陣列、審閱者的一層思維負擔）卻無收益的操作。一個實用的
判斷原則是：在新增 `useCallback` 之前，先識別哪個 `React.memo` 子元件或哪個 hook 依賴項需要
穩定的參考。若兩者都不存在，`useCallback` 就是不需要的。這一原則在程式碼審查時同樣有用：當看
到一個 `useCallback` 時，應能立即找到它所服務的 `React.memo` 子元件或 hook 依賴項；若找不到，
這個 `useCallback` 很可能是可以安全移除的不必要複雜度。

## 範例

```jsx
// ExpensiveList 只在 items 或 onSelect 的參考改變時重新渲染。
// React.memo 在每次父元件重新渲染時執行淺層 props 比對。
const ExpensiveList = React.memo(function ExpensiveList({ items, onSelect }) {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id} onClick={() => onSelect(item)}>
          {item.name}
        </li>
      ))}
    </ul>
  );
});

function Parent({ items }) {
  const [selected, setSelected] = React.useState(null);

  // 若不使用 useCallback，每次 Parent 渲染都會建立新的函式參考。
  // ExpensiveList 上的 React.memo 會看到 onSelect prop 已改變，並仍然重新渲染。
  // useCallback 保持參考穩定，只要依賴項（此處為空）未改變。
  const handleSelect = React.useCallback((item) => {
    setSelected(item);
  }, []); // 無依賴項：setSelected 由 useState 保持穩定

  return (
    <>
      <ExpensiveList items={items} onSelect={handleSelect} />
      {selected && <p>已選取：{selected.name}</p>}
    </>
  );
}
```

## 常見錯誤

- **對每個元件都「以防萬一」地加上 `React.memo`。** 這在每次每個元件渲染時都增加比對開銷，
  卻未驗證比對成本是否低於其所避免的渲染成本。對於渲染成本低的元件，比對本身反而是更昂貴的
  操作。這種做法還有另一個隱性代價：`React.memo` 建立了一個額外的元件包裝層，使得在 React
  DevTools 中追蹤元件時更難對應到原始程式碼。只在 Profiler 量測顯示瓶頸的地方才套用
  `React.memo`。
- **為了消除 lint 警告而從 `useMemo` 或 `useCallback` 中遺漏依賴項。** lint 警告的存在，是因
  為遺漏的值在 hook 內部被讀取。抑制警告並不修復過時閉包，只是隱藏了它。函式將持續讀取過去某
  次渲染的值，直到 hook 因其他原因重新執行。這類錯誤特別隱蔽，因為在開發期間可能表現正常，只
  在特定的時序條件下才暴露問題。應納入該依賴項，讓記憶化正確失效，或重構程式碼使該值不再需要
  在 hook 內部使用。
- **對未傳遞給已記憶化子元件的函式使用 `useCallback`。** 只在元件本身事件處理器中使用的函式，
  不需要參考穩定性。沒有外部消費者比對其參考。將其包裹在 `useCallback` 中，只是增加了需要維護
  的依賴陣列和一層思維負擔，沒有任何執行期的收益。這是新加入 React 團隊的工程師最常犯的錯誤之
  一，因為他們理解了 `useCallback` 的作用，但尚未建立「哪個消費者需要穩定的參考？」的判斷直覺。
- **記憶化前不先量測。** 憑直覺而非 Profiler 資料應用記憶化，會導致元件過度工程化，使其更難
  重構。使用 Profiler 錄製一次互動並識別哪些渲染緩慢，不過一分鐘。這一分鐘花在量測上，能節省
  日後維護不必要記憶化所需的數小時。
- **忘記 `React.memo` 只執行淺層比對。** 若一個 prop 是行內建構的物件——例如
  `<MemoChild config={&#123;&#123; flag: true &#125;&#125;} />`——`React.memo` 在每次父元件渲染時都會看到新的參考，
  並仍然重新渲染子元件。父元件必須用 `useMemo` 穩定參考，或將物件提升到元件外部，`React.memo`
  才能發揮效果。這個錯誤在引入 `React.memo` 後仍觀察不到效能改善時是最常見的診斷方向，應首先
  檢查傳遞給被記憶化元件的每個物件、陣列、函式 prop 的來源，確認其參考是否在父元件渲染間保持
  穩定。

本文所描述的三個 API——`React.memo`、`useMemo`、`useCallback`——在未來版本的 React 生態系中，
將越來越多地由 React Compiler 自動處理。即便如此，理解它們的工作原理與適用條件，對於診斷效能
問題、評估編譯器輸出的正確性，以及在 React Compiler 不可用的環境中進行手動最佳化，仍然是不可
或缺的基礎知識。記憶化的機制不會消失，只是人工標記的需求會逐漸減少；而判斷何時需要記憶化的洞察
力，將持續是資深前端工程師的核心能力之一。在升級至 React 19 並啟用 React Compiler 的過渡期，
建議團隊先確保現有的手動記憶化是正確且有量測依據的，再移交給編譯器自動管理，以確保遷移過程中
效能行為的可預期性。

  的必讀背景資料，也清楚說明了自動記憶化的適用邊界與已知限制

  元件，並確認記憶化套用後效果是否符合預期，使效能診斷的流程更加系統化
