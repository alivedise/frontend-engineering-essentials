# [FEE-501] 元件組合模式

:::info
組合是從簡單元件構建複雜 UI 的主要機制。現代前端架構傾向於將小型、專注的元件組合在一起，而非使用繼承或配置物件。
:::

## 背景

當元件超出單一職責時，直覺通常是新增 props：`showHeader`、`variant`、`mode`。這會導致擁有數十個 props 和複雜條件渲染的「神元件」。組合以不同方式解決這個問題：組裝多個小元件，取代配置一個大元件。

## 模式

### 插槽 / Children（內容投射）

父元件控制子元件中顯示什麼內容。子元件控制內容在哪裡以及如何渲染。

```html
<!-- 框架無關概念：基於插槽的組合 -->

<!-- 父元件決定內容 -->
<Card>
  <CardHeader>使用者檔案</CardHeader>
  <CardBody>
    <Avatar src="user.jpg" />
    <p>歡迎回來，Alive。</p>
  </CardBody>
</Card>

<!-- Card 元件定義佈局，而非內容 -->
```

**何時使用：** 當元件提供結構（佈局、樣式、行為）但內容因使用場景而異時。

### 複合元件

一組設計為協同工作的元件，透過共同的父元件共享隱式狀態。

```html
<!-- Select 管理狀態；Option 和 Trigger 從中讀取 -->
<Select>
  <SelectTrigger>選擇水果</SelectTrigger>
  <SelectContent>
    <SelectOption value="apple">蘋果</SelectOption>
    <SelectOption value="banana">香蕉</SelectOption>
  </SelectContent>
</Select>
```

**何時使用：** 當一組元件代表單一邏輯部件（select、accordion、tabs、dialog）並需要協調行為時。

### 渲染委派（無頭元件）

提供行為和狀態但不提供 UI 的元件。使用者提供渲染。

```js
// 無頭切換元件──提供狀態，不提供 DOM
function useToggle(initial = false) {
  let isOn = initial;
  return {
    get isOn() { return isOn; },
    toggle() { isOn = !isOn; },
    setOn() { isOn = true; },
    setOff() { isOn = false; },
  };
}

// 使用者提供所有渲染
const { isOn, toggle } = useToggle();
```

**何時使用：** 當行為可重用但視覺呈現在不同上下文中差異顯著時。

### 容器 / 展示分離

將資料取得和業務邏輯（容器）與渲染（展示）分離。

```
容器：取得資料、處理錯誤、管理載入狀態
    |
    v
展示：接收 props、渲染 UI、發出事件
```

**何時使用：** 當元件混合資料關注點和顯示時。展示元件變得易於獨立測試和使用不同資料來源重用。

## 最佳實踐

**優先使用組合而非繼承來重用元件。** 元件 MUST 透過定義良好的介面溝通（props 向下、events 向上、slots 用於內容注入），而非透過類別層次結構共享行為。JavaScript 繼承會產生緊密耦合，使元件更難獨立測試和重構。

**讓每個元件專注於單一關注點。** 元件 SHOULD 做好一件事：管理資料與行為，或渲染 UI，而非在規模擴大後同時承擔兩者。當元件開始處理多個不相關的職責時，應將其分解為更小、更專注的元件，再於更高層級進行組合。

**使用插槽與 children 模式提升佈局彈性。** 負責渲染結構包裝器（卡片、面板、對話框）的元件 SHOULD 接受 children，而非透過 props 接受內容。這使包裝器與所框架的內容解耦，讓包裝元件無需修改 props 即可跨情境重用。

**在適當層級進行組合，避免 props 穿透。** 你 SHOULD NOT 將狀態傳遞超過兩到三個中間層元件。當 props 流經多個不使用它的層時，代表元件樹需要重構。將組合提升到更高層級，或在適當邊界引入 context 與狀態管理。

## 常見錯誤

**過度組合簡單 UI。** 並非所有東西都需要三層抽象。一個只渲染文字的按鈕不需要 `ButtonContainer`、`ButtonPresenter` 和 `ButtonLabel`。在有真正理由時才組合：重用、可測試性或關注點分離。

**過早建立過於通用的元件。** 先建立具體版本。只有當你有 2-3 個具體使用場景共享相同結構時，才提取通用模式。過早泛化會建立無法良好服務任何使用場景的元件。
