# `this` 綁定與情境邊界案例

`this` 在 JavaScript 中並不指向它所出現的函式。它指向的是函式被呼叫當下的執行情境
物件。一個函式可以在某個情境中定義，卻在另一個情境中被呼叫，而 `this` 追蹤的是
呼叫點，而非定義點。有一個重要例外：箭頭函式。`this` 在 JavaScript 中經常被誤解。
這種困惑不是源於複雜性。它源於違反了開發者的直覺，即變數會在撰寫之處綁定。`this`
不是一個變數。它是一個隱式參數，在呼叫發生的瞬間解析，而解析規則一旦理解便具有
一致性。

`this` 的解析遵循四條綁定規則，以優先順序排列：new 綁定（以 `new` 呼叫）、
顯式綁定（`call`、`apply`、`bind`）、隱式綁定（作為物件方法呼叫），以及預設
綁定（作為普通函式呼叫）。箭頭函式不參與上述任何規則；它們在定義時從外層詞法
作用域詞法捕獲（lexically capture）`this`，並且無法被重新綁定。優先順序是嚴格的：
`new` 覆蓋顯式，顯式覆蓋隱式，隱式覆蓋預設。理解這個順序消除了猜測的必要性。
在任何呼叫點，只要檢視呼叫形式，就能確定正確的 `this`。

`this` 的困惑源於開發者的直覺期待（詞法的，像變數一樣）與實際運作方式（動態的，
基於呼叫點）之間的落差。類別方法、事件處理器和回呼函式（callback），各自都有
`this` 不符合讀者預期的場景。在類別中定義的方法，一旦被提取並作為回呼傳遞，就
會失去其接收者。相對地，定義在方法內部的箭頭函式，會永久捕獲外層的 `this`，無法
被指向其他對象。這正是使箭頭函式成為類別程式碼中回呼慣用寫法的原因。
從語言設計的角度來看，`this` 的動態性是刻意為之的：
它允許同一個函式在不同的物件上下文中重複使用，這是 JavaScript 以原型為基礎的物件
模型的核心設計。代價是需要開發者主動管理呼叫點的綁定。理解 `this` 的開發者能夠
利用這種靈活性；不理解的開發者則常常只是不斷引入難以追蹤的錯誤。

## 背景

一個方法以 `obj.method()` 呼叫時運作正常，但把同一個函式參考作為回呼傳入（例如傳給 `setTimeout` 或事件監聽器），就拋出錯誤或輸出錯誤結果。差異在於 `this` 的綁定：方法呼叫時 `this` 綁定到物件，但作為普通函式呼叫時，`this` 在嚴格模式下是 `undefined`，在非嚴格模式下則是全域物件。理解 `this` 在呼叫時如何決定，以及箭頭函式、`bind` 和顯式綁定各自在什麼情況下是解法，才能根除這類 JavaScript bug 的根源。

## 設計思維

### 四條綁定規則

四條綁定規則構成了一個優先層級體系，決定每個呼叫點的 `this`。new 綁定在以
`new` 關鍵字呼叫函式時適用：建立一個新物件，其原型被設定為建構子的 `prototype`
屬性，建構子內的 `this` 指向該新物件，並在建構子未明確回傳其他物件時予以回傳。
new 綁定具有最高優先順序，並覆蓋任何透過 `bind` 附加到同一函式上的顯式綁定。

顯式綁定在以 `.call(thisArg, ...args)`、`.apply(thisArg, args)` 或
`.bind(thisArg)` 呼叫函式時適用。三者都以預期的接收者作為第一個參數。`.bind`
與 `.call` 和 `.apply` 的區別在於它回傳一個新函式而非立即呼叫；回傳的函式
`this` 被永久固定，無法被另一個 `.bind` 或作為方法呼叫的方式再次覆蓋。
顯式綁定優先於隱式綁定。

隱式綁定在函式作為物件屬性被呼叫時適用：`obj.method()`。點左側的物件在該次
呼叫期間成為 `this`。綁定是淺層的：只有緊鄰的外層物件有影響，與函式可能定義
在的任何外層情境無關。若方法被儲存在變數中並在沒有物件參考的情況下呼叫，
隱式綁定不再適用，呼叫退化為預設綁定。

預設綁定在上述三條規則均不匹配時適用：沒有接收者、沒有明確的 `thisArg`、也
沒有 `new` 的普通函式呼叫。在嚴格模式下，預設綁定將 `this` 解析為 `undefined`。
在非嚴格模式下，解析為全域物件（瀏覽器中為 `window`，Node.js 中為 `global`）。
嚴格模式與非嚴格模式之間的這種不對稱性，是許多細微錯誤的根源：非嚴格模式的
預設綁定靜默地污染或讀取全域物件，而嚴格模式在存取 `this` 屬性時產生明確的
`TypeError`。

在呼叫點應用規則的方法：找到被呼叫的函式；檢視呼叫形式。若有 `new`，適用 new
綁定。若有 `.call`、`.apply` 或 `.bind`，適用顯式綁定。若函式作為物件屬性被
呼叫（`obj.fn()`），適用隱式綁定。若均不符合，適用預設綁定。若函式是箭頭函式，
四條規則均不適用：`this` 繼承自定義時外層詞法作用域的 `this`，且不可更改。

這個演算法的機械性正是它的價值所在。`this` 相關的除錯錯誤幾乎都是因為開發者
跳過了這個步驟，直接依賴直覺而非系統性地檢視呼叫形式。對於新接觸 JavaScript
的開發者，建議在遇到任何 `this` 相關錯誤時，先以文字描述「這個函式是如何被呼叫
的」，再對應到四條規則中的一條。若不能用文字清晰描述呼叫形式，問題往往在於對
程式控制流程的理解，而非對 `this` 規則本身的理解。理解呼叫點是理解 `this` 的
先決條件，而非選項。

### 箭頭函式與詞法 this

箭頭函式在測試場景中也有一個值得注意的行為。由於箭頭的 `this` 在定義時被捕獲，且對 `call`、`apply` 和 `bind` 完全免疫，試圖透過這些方法注入不同接收者的測試將靜默地失敗。箭頭函式忽略顯式接收者，繼續使用被捕獲的 `this`。這意味著針對使用類別欄位箭頭的程式碼，測試中無法透過標準的動態綁定機制替換 `this`；測試必須在建構時設定正確的 `this`，即構造一個具有所需狀態的真實實例，而不是試圖在呼叫時注入模擬物件。理解這個限制，對於在不破壞測試隔離性的前提下設計可測試的類別架構至關重要。

箭頭函式不是普通函式的語法糖。它們是一種擁有根本不同 `this` 語意的不同函式種類。
它們沒有自己的 `this`，也沒有 `arguments` 物件。它們不能用作建構子：以 `new` 呼叫
箭頭函式會拋出 `TypeError`。當箭頭函式被求值時，JavaScript 引擎從外層詞法作用域
捕獲當前的 `this` 值，並將其永久關聯到該箭頭函式上。之後無論以何種方式、在何處
呼叫該箭頭函式，都使用那個被捕獲的值。這個捕獲發生在函式運算式被求值的那一刻，
而非在函式被宣告的那一刻；若箭頭定義在一個稍後才執行的方法中，捕獲在方法執行
時發生，而非在類別定義被解析時。

這對巢狀函式有重要影響。在方法內定義的普通函式，除非明確綁定，否則會失去方法的
`this`；在同一位置定義的箭頭函式，則自動繼承方法的 `this`。箭頭的 `this` 在
外層函式執行時決定（在物件建構時、在方法被呼叫時），而非在箭頭被呼叫時。
在方法中撰寫箭頭函式，是一個簡潔的聲明：箭頭的行為依賴方法的接收者，且這種
依賴是明確且不可打破的。在 `Promise` 鏈或 `async/await` 函式中，普通函式回呼
會在每個 `.then()` 中重新建立 `this` 的問題；箭頭函式讓整個非同步流程都使用
同一個外層 `this`，使非同步類別方法的撰寫大幅簡化。

### 嚴格模式的影響

嚴格模式的預設綁定對除錯的影響值得特別強調。在非嚴格模式中，被提取的方法以預設
綁定呼叫時，會靜默地讀取和寫入全域物件：`this.count++` 悄悄地建立或遞增
`window.count`，錯誤只有在全域污染導致其他地方的意外副作用時才浮現。在嚴格模式
中，同樣的呼叫立即在誤用點拋出 `TypeError`。雖然 `TypeError` 看起來是更糟的結果，
但從工程角度它嚴格意義上更優：失敗精確地定位在綁定錯誤發生的位置，而非在距離很
遠的地方被觀察到全域狀態損壞。

ES 模組、類別主體和明確的 `'use strict'` 指令都會啟用嚴格模式，這意味著現代
JavaScript 的大多數寫法預設都受到嚴格模式保護。只有閱讀遺留的非模組腳本或舊版函
式庫時，才需要考慮非嚴格模式的靜默全域污染行為。

### 類別欄位與方法綁定

JavaScript 類別提供了兩種將函式附加到實例的方式。原型方法（在類別主體中宣告
的 `onClick() { ... }`）存在於類別的 `prototype` 物件上。所有實例共享同一個
函式物件；`this` 在每次方法被呼叫時動態解析。若以 `instance.onClick()` 的形式
呼叫，隱式綁定給出正確的 `this`。若作為回呼傳遞
（`button.addEventListener('click', this.onClick)`），隱式綁定將會丟失。

類別欄位箭頭（在類別主體層級使用類別欄位提案宣告的 `onClick = () => { ... }`）
在建構時每個實例各求值一次。每個實例都獲得自己的箭頭函式副本，`this` 已被捕獲
為該實例。代價是記憶體：每個實例一個函式物件，而非原型上的一個共享函式。對於
擁有數千個實例的類別，這個差異是可量測的。對於 UI 元件的常見情況（至多數十到
數百個實例），開銷可忽略不計，而綁定安全性物有所值。類別欄位模式是 React 類別
元件中的慣用寫法，也是傳遞為事件處理器 prop 的方法之標準推薦做法。值得注意的
是，類別欄位並非 `prototype` 的一部分，因此子類別若以 `super.onClick()` 呼叫
也只會得到同一個捕獲了父類別實例的箭頭，而非觸發多型覆寫。對於需要被子類別
覆寫的方法，原型方法是正確的選擇，並在呼叫點提供正確的綁定形式。

類別欄位箭頭模式對繼承有一個重要的隱含義：因為類別欄位在建構時每個實例各自求值，
而非共享於原型上，子類別無法透過在自身原型上定義同名方法來覆寫父類別的類別欄位
箭頭。子類別的原型方法永遠不會被找到，因為實例屬性在原型鏈被查詢之前就已被找到。
使用類別欄位箭頭作為事件處理器的團隊必須意識到，繼承的箭頭無法透過正常的基於原型
的子類別化來覆寫；覆寫需要讓父類別方法成為原型方法，或在子類別上以同名定義類別欄
位箭頭，後者會建立一個新的每實例函式來遮蔽父類別的。這個設計決策影響框架元件的繼
承策略：React 的函式元件和 hooks 完全迴避了這個問題，因為它們不使用 `this`，但在
使用類別元件或 Web Components 的程式庫中，理解這一限制對正確設計元件的繼承層次至
關重要。

### 事件處理器中的 this

`addEventListener('click', this.handle)` 是常見的 `this` 相關錯誤來源。
當瀏覽器呼叫該處理器時，它在沒有接收者的情況下呼叫被提取的函式；`this` 在嚴格
模式下變為 `undefined`。有三種常見的解決方式。`.bind(this)` 建立一個永久綁定的
函式：`addEventListener('click', this.handle.bind(this))`。這能奏效，但有一個
缺點：綁定函式在每次該表達式被求值時都是新物件，因此除非儲存綁定後的參考，否則
`removeEventListener` 無法移除它。箭頭包裝器
（`addEventListener('click', (e) => this.handle(e))`）透過詞法閉包保留 `this`
並傳遞事件；它有同樣的可儲存性問題，但可讀性好且不需要修改方法本身。類別欄位
箭頭（`handle = (e) => { ... }`）是最簡潔的解決方案：在建構時綁定，作為穩定
的實例屬性儲存，可直接傳遞給 `addEventListener`，並在之後以
`removeEventListener(this.handle)` 使用同一個穩定參考移除。當類別欄位不可用時，
內聯箭頭包裝器是現代首選模式；顯式 `.bind` 是可接受的，但之後更難移除。

`this` 的問題在 Web Components 中格外顯著。自訂元素（custom element）的生命週期
回呼（`connectedCallback`、`disconnectedCallback`、`attributeChangedCallback`）
由瀏覽器直接以方法形式呼叫，隱式綁定正常運作。但若在 `connectedCallback` 中以
`document.addEventListener('keydown', this.onKey)` 的方式添加文件層級的事件監聽，
`this.onKey` 在被呼叫時就失去綁定。正確的模式是在建構子中以類別欄位箭頭定義所
有需要作為獨立回呼使用的方法，並在 `disconnectedCallback` 中以同一個穩定參考呼叫
`removeEventListener`，避免元素卸載後監聽器殘留造成的記憶體洩漏。

### 嚴格模式下的 this

嚴格模式下的預設綁定將 `this` 解析為 `undefined`，而非全域物件。這將被提取方法
的失敗模式，從靜默的全域污染改變為立即的 `TypeError: Cannot read properties of
undefined`。雖然 `TypeError` 看起來更具破壞性，但從除錯的角度來看它嚴格意義上
更優：錯誤出現在誤用點，而非在許多執行幀之外以對全域狀態莫名的修改形式顯現。
嚴格模式自動應用於 ES 模組、類別主體，以及任何以 `'use strict'` 開頭的函式。
在實際應用中，大多數現代 JavaScript 預設在嚴格模式下執行，因此在生產程式碼中
很少遇到非嚴格模式的全域綁定行為。理解它對於閱讀舊版程式碼，以及理解某些舊版
API 在嚴格情境下為何表現異常，仍然是必要的。瀏覽器中的內嵌事件處理器
（`onclick="..."` HTML 屬性）在非嚴格模式下執行，這也是為何部分遺留程式碼的
`this` 行為在移植到模組環境後突然發生變化。嚴格模式使原本被全域物件「吸收」
的錯誤變成了可見的 `TypeError`，顯露了原本就存在的綁定缺陷。

## 最佳實踐

**禁止（MUST NOT）假設從物件中提取出的方法仍保有其 `this` 綁定。** 將 `const fn = obj.method` 賦值後再呼叫 `fn()`，會在沒有隱式接收者的情況下呼叫函式；在嚴格模式下，`fn` 內部的 `this` 解析為 `undefined`，在非嚴格模式下解析為全域物件。這適用於所有情況：將方法賦值給變數、作為回呼傳遞給高階函式、儲存在陣列中，或從物件中解構，都將函式從其原始接收者中提取出來，導致綁定丟失。保留綁定的唯一方式，是以 `obj.method()` 的形式就地呼叫、使用 `.bind(obj)` 建立永久綁定的函式，或使用在閉包中捕獲物件的箭頭包裝器。

**必須（MUST）對作為回呼或事件處理器傳遞、且需要存取外層類別的 `this` 的方法，
使用箭頭函式。** 定義為類別欄位的箭頭函式（`handleClick = (e) => { ... }`）
在建構時將 `this` 綁定到實例，可直接傳遞給 `addEventListener` 或作為 React prop，
無需 `.bind()`。綁定在建構時建立一次，作為穩定的實例屬性儲存，無論方法在之後
以何種方式、在何處被呼叫，都保證是正確的。這是 React 類別元件和基於類別框架中
的慣用模式。它從根源上消除了整類 `this` 相關錯誤，因為它在定義點就使接收者
明確，而非依賴每個呼叫點的正確呼叫形式。

**禁止（MUST NOT）在 `render()` 內或 JSX 屬性中的效能關鍵元件裡使用
`.bind(this)`。** `.bind()` 在每次呼叫時建立一個新的函式物件。在 JSX 中使用時
（`onClick={this.handleClick.bind(this)}`），每個渲染週期都會建立一個新函式。
這導致渲染之間的引用不等：`React.memo` 和 `shouldComponentUpdate` 以引用比較
props，而每次渲染的新函式物件使兩者的優化失效，導致子元件不必要的重新渲染。
在函式元件中，JSX 中的內聯箭頭函式也存在同樣的問題：`onClick={() =>
this.handleClick()}` 在每次渲染時建立一個新閉包。解決方案是將綁定方法定義為
類別欄位（在類別元件中），或使用 `useCallback` 穩定回呼（在函式元件中），使
相同的函式引用在依賴項未變更時跨渲染重複使用。這個原則同樣適用於傳遞給虛擬
DOM 之外的回呼，例如 `MutationObserver`、`IntersectionObserver` 或 Web Worker
訊息處理器：若每次效果執行都建立新的函式，而清理函式無法正確移除舊的監聽器，
就會造成監聽器洩漏，累積的監聽器數量隨每次重新渲染而增長。

**應該（SHOULD）在除錯 `this` 相關錯誤時，套用四規則演算法，而非靠猜測。**
識別函式在特定呼叫點的呼叫方式：以 `new`、以 `call`/`apply`/`bind`、以
`obj.method()` 的形式，或作為普通呼叫。為該呼叫形式套用對應的規則。若函式是
箭頭函式，`this` 是箭頭定義時外層作用域中的 `this`。追溯到箭頭建立的位置，
並檢視那個外層作用域在那一時刻的 `this`。這個演算法是機械性的，並且總是給出
正確答案。根據函式定義的位置猜測，或假設方法作為回呼傳遞時仍保有其接收者，
會產生錯誤的診斷，並導致掩蓋而非修復底層綁定問題的補丁。在程式碼審查中，這個
演算法同樣可作為審查框架：當看到函式被傳遞為回呼時，審查者應在心中快速執行
四規則演算法，確認在接收函式呼叫它的方式下，`this` 是否為作者預期的值。若無
法從審查的程式碼中確定呼叫形式，應要求作者在說明中明確這一點，或添加測試驗證
`this` 的正確性。`this` 錯誤是靜默的，在非嚴格模式中更是如此，預防遠比事後
除錯來得高效。

## 範例

```js
class Timer {
  constructor() {
    this.count = 0;
  }

  // 錯誤寫法 — 在嚴格模式下作為回呼傳遞時，'this' 為 undefined
  startBroken() {
    setInterval(function() { this.count++; }, 1000);
  }

  // 箭頭函式 — 'this' 詞法綁定到 Timer 實例
  start() {
    setInterval(() => { this.count++; }, 1000);
  }

  // 類別欄位 — 在建構時綁定，可直接作為參考傳遞
  tick = () => { this.count++; };

  startWithField() {
    setInterval(this.tick, 1000);
  }
}

const timer = new Timer();
timer.start();        // 正常運作：箭頭捕獲 Timer 實例作為 this
timer.startBroken();  // 嚴格模式下 TypeError：無法讀取 undefined 的 'count'
```

## 常見錯誤

將 `obj.method` 作為回呼傳遞而不綁定，是普遍的錯誤。方法從物件中被提取；
隱式接收者並未隨之攜帶。回呼觸發的瞬間，方法內部的 `this` 在嚴格模式下為
`undefined`。解決方案是類別欄位箭頭、呼叫點的箭頭包裝器，或儲存的 `.bind(obj)`
結果，不需要三者同時使用。

在 `render()` 或 JSX 屬性中使用 `.bind(this)`，會在每次渲染時建立新的函式物件。
接收該 prop 的子元件將總是看到新的引用，使 `React.memo` 和
`shouldComponentUpdate` 中的淺比較失效。綁定後的方法引用應當是穩定的：在建構
時建立一次（類別欄位），或以 `useCallback` 記憶化。

期待 `call`、`apply` 或 `bind` 能重新綁定箭頭函式，是常見的誤解。這些方法對
箭頭的 `this` 毫無作用。箭頭的 `this` 在定義時被捕獲，且不可更改。以
`.call(differentObj)` 呼叫箭頭函式並不會改變 `this`；箭頭完全忽略顯式接收者，
並使用其捕獲的詞法 `this`。這個行為在測試場景中尤為值得注意：若測試程式碼嘗試
以 `.call(mockObj)` 替換箭頭的接收者來注入測試替身，這個嘗試將靜默地失敗，且
不會拋出任何錯誤，導致測試使用了真實物件的 `this` 而非測試預期的替身。

將類別欄位箭頭的每實例記憶體成本與原型方法共享相混淆，導致過早的過度優化。
對大多數 UI 元件而言，每個實例多一個函式物件的成本微不足道。在極少數類別被
實例化數千次且記憶體是瓶頸的情況下，呼叫點的箭頭包裝器（而非類別欄位）
在提供正確綁定的同時保留了原型方法共享。優化應以分析工具測量的實際資料為依據，
而非對函式物件成本的直覺假設。在決定是否從類別欄位箭頭改回原型方法時，
正確的衡量標準是記憶體分析器中可觀察到的堆積壓力，而非程式碼行數或函式個數。
框架層的效能建議（如 React 文件中的 `useCallback` 使用時機）是基於實測資料的，
應優先遵循，而非自行猜測哪種綁定模式更省記憶體。

在非同步程式碼中，`async` 方法內部的 `await` 後面若跟著存取 `this` 的普通函式，
也常造成困惑。`async` 函式本身具有普通函式的 `this` 語意；若作為方法呼叫，
隱式綁定適用。在 `await` 之後，`this` 的值並不改變，微任務恢復執行時，
閉包中的 `this` 與暫停前相同。但若 `async` 方法被提取為回呼再呼叫，就與普通
方法提取有同樣的問題：`this` 在恢復時仍是 `undefined`（嚴格模式）。類別欄位
箭頭搭配 `async` 的寫法（`fetchData = async () => { ... }`）同樣有效，且是
最安全的選擇。
