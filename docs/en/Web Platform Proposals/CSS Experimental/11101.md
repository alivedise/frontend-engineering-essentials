# [FEE-11101] @starting-style — Entry Animations Without JavaScript

:::info
Define where an element's transition begins, so dialogs, toasts, and dropdowns can animate into view with pure CSS — no JavaScript timing hacks required.
:::

:::info Baseline Newly Available
Supported in Chrome 117+, Firefox 129+, Safari 17.5+. Use progressive enhancement for older browsers.
:::

## Context

CSS `transition` animates between two computed states. To do so, it needs a "before" value and an "after" value for every property being animated. This works perfectly when an element is already in the DOM and visible — changing `opacity` from `1` to `0`, or `transform` from `none` to `translateY(-8px)`, gives the browser a clear before and after.

The problem arises with elements that are hidden via `display: none`. When an element has `display: none`, the browser does not render it. It has no computed box, no geometry, and no interpolable property values. When you switch it to `display: block`, CSS transitions have no starting state to animate from — the element simply appears at its final state instantly.

For years, the workaround was a JavaScript timing hack:

```js
// Show the element first (establishing a computed state)
element.style.display = 'block';
// Then, on the next frame, add the class that triggers the transition
requestAnimationFrame(() => element.classList.add('visible'));
```

The `requestAnimationFrame` callback fires after the browser has painted the element at its initial state, giving the transition a "before" value to interpolate from. This works, but it is fragile: it couples what should be a pure CSS presentation concern to JavaScript, and the timing is technically implementation-dependent.

Chrome 117 introduced two related capabilities simultaneously:

1. **`@starting-style`** — an at-rule that explicitly declares the initial computed values for a transition when an element first becomes visible.
2. **Animatable `display`** — the `display` property can now participate in CSS transitions, allowing `display: none` → `display: block` to be part of a smooth animated sequence.

Together these two features close the gap entirely. Entry animations that previously required JavaScript can be expressed as pure CSS declarations.

## Scenario

You are building a notification system where toast messages slide in from above when they appear and fade out when dismissed. Requirements:

- Entry: fade in and slide down from `-12px` above final position.
- Exit: fade out and slide up back to `-12px`.
- No JavaScript for the animation timing — only for the business logic of showing and hiding the toast.
- Respect the user's motion preference.

With `@starting-style`, the entry animation requires no JS timing tricks. The CSS declares the starting state; the browser handles the interpolation.

## Best Practices

- MUST include `@starting-style` alongside any `transition` that animates element entry. Without it, there is no starting state, and the transition does not play on first render or when transitioning from `display: none`.
- MUST use the `allow-discrete` keyword when transitioning `display` or `visibility`. These are discrete properties — they do not interpolate numerically. The `allow-discrete` flag tells the browser to delay the discrete change until the end of the transition (for exit) or apply it immediately at the start (for entry). Syntax: `transition: opacity 0.3s, display 0.3s allow-discrete`.
- MUST NOT use `@starting-style` for exit animations. It only applies when an element is first rendered or transitions out of `display: none`. For exit, define the hidden state in a selector rule targeting the hidden state (e.g., `:not(:popover-open)`).
- SHOULD wrap all entry/exit animation CSS in `@media (prefers-reduced-motion: no-preference)` to avoid triggering vestibular disorders in sensitive users.
- SHOULD use `@starting-style` nested inside the element's existing rule block where the spec allows nesting — this keeps the starting state co-located with the transition declaration and is easier to maintain.
- MAY also use `@starting-style` for elements that are newly inserted into the DOM, not just those transitioning from `display: none`. The rule fires whenever the element first gets a computed style.

## Design Thinking

### Why CSS transitions could not animate entry before

CSS transitions require two computed style snapshots: the value before the change and the value after. The browser captures the "before" snapshot, then applies the new CSS, captures the "after" snapshot, and interpolates between them over the specified duration.

When an element has `display: none`, it is outside the formatting context entirely. The browser maintains no computed box, no geometry, and no property values for it. The moment `display` changes to `block`, the browser creates a new layout box from scratch — there is no "before" snapshot, so no transition fires.

### How JavaScript hacks compensated

The `requestAnimationFrame` trick works because it forces the browser to commit a rendering frame with the element at its initial state before the transition-triggering class is added. After that initial paint, the "before" snapshot exists and the transition fires normally.

Other workarounds included:

- **`visibility: hidden` instead of `display: none`** — `visibility` is an animatable discrete property, so elements remained in the layout flow (taking up space) even when hidden, preserving the computed box. This solved the transition problem but had layout side effects.
- **`@keyframes` animation with `animation-fill-mode: forwards`** — using `@keyframes from { opacity: 0 }` sidesteps the transition problem entirely since keyframes always have an explicit starting frame. The cost is more verbose CSS and less composability with the `transition` property.
- **Double `requestAnimationFrame`** — some libraries used two nested rAF calls to guarantee two rendered frames before triggering the class, working around inconsistent behavior in certain browsers.

### Why `@starting-style` is the right model

`@starting-style` is explicit about intent. It answers the question: "where does this element start animating from?" directly in CSS, without relying on paint-timing coincidences or JavaScript orchestration. The browser's job becomes unambiguous: use the values in `@starting-style` as the interpolation start point, then transition to the values in the element's normal rule.

This also makes the code easier to understand. The starting state, the ending state, and the transition timing are all in the stylesheet. A developer reading the CSS knows exactly what the entry animation looks like without tracing JavaScript.

## Example

A dialog using the Popover API that fades in and slides down from above when opened, and fades out and slides up when closed. The full animation is pure CSS — the `popovertarget` attribute on the buttons handles open/close without any JavaScript.

```html
<button popovertarget="my-dialog">Open dialog</button>

<div id="my-dialog" class="dialog" popover>
  <p>Hello from the dialog!</p>
  <button popovertarget="my-dialog" popovertargetaction="hide">Close</button>
</div>
```

```css
/* Base layout — always applied */
.dialog {
  padding: 2rem;
  border-radius: 8px;
  border: 1px solid #e2e8f0;
  background: #fff;
  box-shadow: 0 8px 24px rgb(0 0 0 / 0.12);
  max-width: 480px;
  width: 90%;
}

@media (prefers-reduced-motion: no-preference) {
  /* Final (open) state */
  .dialog:popover-open {
    opacity: 1;
    transform: translateY(0);
  }

  /* Transition declaration — includes display so the popover
     can animate out before being removed from the top layer */
  .dialog {
    transition:
      opacity 0.25s ease,
      transform 0.25s ease,
      display 0.25s allow-discrete,
      overlay 0.25s allow-discrete;
  }

  /* Entry: starting state when the dialog first becomes visible */
  @starting-style {
    .dialog:popover-open {
      opacity: 0;
      transform: translateY(-12px);
    }
  }

  /* Exit: animate toward the hidden state before display:none applies */
  .dialog:not(:popover-open) {
    opacity: 0;
    transform: translateY(-12px);
  }
}
```

### How the entry works

When the popover opens:

1. The browser applies `:popover-open` to the dialog, making it part of the top layer.
2. Because `display: none` → displayed is a discrete change with `allow-discrete`, the display change happens immediately at the start of the transition.
3. `@starting-style` provides the initial computed values: `opacity: 0`, `transform: translateY(-12px)`.
4. The transition interpolates from the `@starting-style` values to the `:popover-open` values (`opacity: 1`, `transform: translateY(0)`) over 250 ms.

### How the exit works

When the popover closes:

1. The browser removes `:popover-open`, which activates the `:not(:popover-open)` rule (`opacity: 0`, `transform: translateY(-12px)`).
2. The `display` and `overlay` transitions (both with `allow-discrete`) delay the discrete changes until the end — the element stays visible and in the top layer while the opacity and transform animate.
3. After 250 ms, the transition ends, the top-layer membership and `display: none` apply, and the element disappears.

### Progressive enhancement fallback

Without the `@media (prefers-reduced-motion: no-preference)` wrapper, the popover still opens and closes correctly — it simply appears and disappears without animation. Browsers that do not support `@starting-style` also show the popover without animation rather than breaking.

```css
/* Optional @supports guard for stricter progressive enhancement */
@supports (selector(:popover-open)) {
  @media (prefers-reduced-motion: no-preference) {
    /* animation rules here */
  }
}
```

## Deep Dive

### `@starting-style` and Shadow DOM

`@starting-style` works inside shadow roots. Rules declared inside a `<style>` element within a shadow tree apply to elements within that shadow root when they first become visible, following the same scoping rules as all other shadow DOM styles.

### `@starting-style` applies to transitions only, not `@keyframes`

`@keyframes` animations already have an explicit first frame — the `from` or `0%` block. They do not need `@starting-style`. The at-rule is exclusively about providing the "before" snapshot for CSS transitions. If you switch from a `transition`-based entry animation to a `@keyframes`-based one, remove `@starting-style` and use `from { opacity: 0; transform: translateY(-12px); }` in the keyframe block instead.

A common point of confusion: `animation-fill-mode: backwards` fills the `from` keyframe before the animation starts, which superficially resembles what `@starting-style` does for transitions. They are unrelated mechanisms — `animation-fill-mode` operates on keyframe timelines, while `@starting-style` operates on the transition system's before/after snapshot model.

### Nesting `@starting-style` inside a selector

The spec supports nesting `@starting-style` inside the rule that it applies to:

```css
.dialog:popover-open {
  opacity: 1;
  transform: translateY(0);
  transition: opacity 0.25s, transform 0.25s, display 0.25s allow-discrete;

  @starting-style {
    opacity: 0;
    transform: translateY(-12px);
  }
}
```

This nested form keeps the starting state co-located with the final state and transition declaration. It is equivalent to the non-nested form and supported wherever `@starting-style` is supported (Chrome 117+, Firefox 129+, Safari 17.5+).

### Specificity inside `@starting-style`

Rules inside `@starting-style` have the same specificity as the equivalent rules outside the block. `@starting-style { .dialog:popover-open { opacity: 0; } }` has the specificity of `.dialog:popover-open` — one class and one pseudo-class. This means you can override `@starting-style` values with higher-specificity selectors just as you would with normal CSS.

### The `overlay` property

`overlay` controls whether an element is in the browser's top layer. It is a discrete property, like `display`, and also requires `allow-discrete` to participate in transitions:

```css
transition: opacity 0.3s, display 0.3s allow-discrete, overlay 0.3s allow-discrete;
```

Including `overlay` in the transition ensures that the browser's top-layer overlay (the backdrop and stacking context that Popover and `<dialog>` elements inhabit) also animates out gracefully. Without it, the top-layer context collapses immediately on close, which can cause the exit animation to appear clipped or to jump. This property has no effect in non-top-layer contexts and can safely be omitted there.

### Interaction with `visibility` vs `display`

If your hidden state uses `visibility: hidden` rather than `display: none`, you do not need `allow-discrete` — `visibility` is already handled by the CSS transition system as a discrete-but-transitioning property. You also do not strictly need `@starting-style` for `visibility`-based show/hide, because `visibility: hidden` elements still have a computed box and property values for transitions to start from. `@starting-style` is most valuable for the `display: none` / Popover / `<dialog>` cases where no prior computed state exists.

### Applying `@starting-style` to newly inserted DOM nodes

`@starting-style` is not limited to elements toggling `display`. It also fires when an element is first inserted into the DOM — for example, a toast notification created dynamically via JavaScript:

```js
const toast = document.createElement('div');
toast.className = 'toast';
toast.textContent = 'File saved.';
document.body.appendChild(toast);
```

```css
.toast {
  position: fixed;
  bottom: 1.5rem;
  right: 1.5rem;
  padding: 0.75rem 1.25rem;
  background: #1e293b;
  color: #fff;
  border-radius: 6px;
  opacity: 1;
  transform: translateY(0);
  transition: opacity 0.3s ease, transform 0.3s ease;
}

@media (prefers-reduced-motion: no-preference) {
  @starting-style {
    .toast {
      opacity: 0;
      transform: translateY(8px);
    }
  }
}
```

When the element is appended to the DOM, the browser assigns its first computed style. `@starting-style` intercepts that moment, providing `opacity: 0` and `transform: translateY(8px)` as the starting values. The transition then plays from those values to the normal rule values (`opacity: 1`, `translateY(0)`), producing the entry animation — no `requestAnimationFrame` required.

For the exit, you would set `opacity: 0` imperatively (or via a class) before removing the element, and listen for the `transitionend` event to call `element.remove()`. The entry (`@starting-style`) and the exit (event-driven removal after CSS transition) each have their natural tool.

Progressive enhancement check:

```css
@supports (selector(:popover-open)) {
  /* @starting-style and popover animations */
}
```

Or via JavaScript:

```js
const supported = CSS.supports('selector(:popover-open)');
```

Because `@starting-style` and the Popover API shipped together in modern browsers, checking for `:popover-open` selector support is a reliable proxy for `@starting-style` support. Browsers that do not support the at-rule silently skip the starting-state block, so entry transitions do not play — elements appear at their final state instantly without any visible breakage.

The `allow-discrete` keyword for `transition` landed in the same browser versions as `@starting-style`. There is no scenario where `@starting-style` is supported but `allow-discrete` is not, so a single feature check covers both.

Internet Explorer and legacy Edge (pre-Chromium) do not support `@starting-style`. These browsers are outside the support matrix for most new projects, but if your target includes them, treat all entry animations as purely decorative and ensure the element's default CSS state is fully visible without animation.
