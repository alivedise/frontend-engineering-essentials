# Utility Types & Type Manipulation

TypeScript ships a library of generic utility types that transform existing types into new ones. These utilities — `Partial`, `Required`, `Readonly`, `Pick`, `Omit`, `Exclude`, `Extract`, `ReturnType`, `Parameters`, `NonNullable`, `Record` — eliminate the need to manually redefine type shapes when a variant is needed. Manually redefined shapes drift when the source type changes; structural derivation stays synchronized automatically.

The most commonly used utilities split into two groups: shape transformers (`Partial`, `Required`, `Readonly`, `Pick`, `Omit`) that produce a modified version of an object type, and function type extractors (`ReturnType`, `Parameters`) that derive types from function signatures. Both groups eliminate duplication between the TypeScript type system and the code it describes.

All built-in utility types are implemented as mapped types — a pattern available to application code as well. When no built-in utility expresses the required transformation, a custom mapped type using `{ [K in keyof T]: ... }` fills the gap.

## Design Thinking

### Derivation vs. duplication

A type that duplicates a subset of another type's fields will silently fall out of sync when the source type evolves. `Pick<User, 'id' | 'name'>` automatically reflects any changes to `User`'s `id` and `name` fields. Duplication creates a maintenance obligation with no enforcement; derivation is self-updating.

### Mapped types: the engine behind utility types

Built-in utilities like `Partial<T>` and `Readonly<T>` are implemented as mapped types: `{ [K in keyof T]?: T[K] }` and `{ readonly [K in keyof T]: T[K] }`. Understanding the pattern lets developers write custom utilities when the built-ins don't fit the use case.

### Template literal types for string manipulation

TypeScript 4.1+ supports template literal types and the string transformation utilities `Uppercase<S>`, `Lowercase<S>`, `Capitalize<S>`, `Uncapitalize<S>`. These enable type-level string manipulation for use cases like event name derivation, CSS property key generation, and API key naming conventions.

## Best Practices

**MUST use `Pick<T, K>` and `Omit<T, K>` rather than redefining type shapes manually when a subset or exclusion of an existing type is needed.** Manual redefinition creates a second source of truth that diverges silently when the source type adds, removes, or renames fields. Structural derivation with `Pick` and `Omit` is a declaration of intent — "this type is this subset of that type" — that TypeScript enforces automatically.

**MUST use `Readonly<T>` for objects passed as configuration, stored as module-level constants, or used as default values.** `Readonly<T>` prevents accidental mutation at call sites with no runtime overhead — the check is compile-time only. For deeply nested objects where shallow readonly is insufficient, use `as const` on the literal value, which produces a deeply readonly type.

**SHOULD use `ReturnType<typeof fn>` and `Parameters<typeof fn>` to derive types from existing function signatures rather than duplicating them.** When a function's signature changes, types derived from `ReturnType` and `Parameters` update automatically. Separately maintained type declarations require a manual update and a human to notice the mismatch.

**SHOULD build custom mapped types when no built-in utility expresses the required transformation.** The pattern `{ [K in keyof T]: ... }` is the foundation of all built-in utilities and is equally available in application code. A custom mapped type that wraps every value in a `Promise` — producing an async version of an object's interface — is idiomatic TypeScript, not an advanced technique reserved for library authors.
