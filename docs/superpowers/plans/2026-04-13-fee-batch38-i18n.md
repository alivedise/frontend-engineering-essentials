  **Opening context (3–4 paragraphs):**
  - Internationalization (i18n) is the engineering process of designing and building a product so that it can be adapted to different languages, regions, and cultures without requiring engineering changes for each adaptation. Localization (l10n) is the content process of actually adapting the product for a specific locale — translating strings, formatting dates in the local convention, and adjusting layout for the local writing direction. i18n is done once by engineers; l10n is done repeatedly by translators and content teams.
  - The distinction matters practically: a product that was not internationalized requires engineering work to add each new locale. A product that was internationalized requires only new translation files. The investment in i18n is front-loaded and scales to any number of locales; the cost of skipping i18n is paid with every new market the product enters.
  - This category covers the full i18n stack: message formatting and the ICU syntax that enables rich string interpolation, pluralization rules that vary by language, the browser's `Intl` API for date/number/currency formatting, RTL layout for Arabic and Hebrew, locale detection and routing, the translation workflow from string extraction to delivery, and i18n in component libraries.

  **`## Design Thinking` subsections:**
  - `### i18n is not just translation` — Translation is one part of localization. Other dimensions: number formatting (1,234.56 in en-US vs 1.234,56 in de-DE), date formatting (MM/DD/YYYY vs DD/MM/YYYY), currency display, plural rules (Russian has four plural forms; English has two), RTL layout, text expansion (German strings are typically 30–40% longer than English equivalents), and cultural idioms. A product that handles only translation and none of these dimensions will be technically localized but practically broken.
  - `### The ICU message format as the standard` — ICU (International Components for Unicode) message format is the industry standard for string internationalization. It supports variable interpolation (`{name}`), plural selection (`{count, plural, one {item} other {items}}`), select (for gender or other categorical choices), and number/date formatting. i18next, FormatJS, and most i18n libraries support ICU syntax. Using a library that supports ICU from the start is the right default.
  - `### Translation as a development workflow concern` — Strings must be extracted from code into message files, sent to translators, and returned as localized files in a managed pipeline. An ad-hoc process — developers manually copy strings into a spreadsheet, a translator edits the spreadsheet, a developer copies strings back — does not scale. String extraction tools (i18next-parser) and translation management systems (Crowdin, Phrase, Lokalise) are the standard solution.

  **`## Best Practices`:**

  **MUST externalize all user-visible strings into message files from the start of the project, not as a retrofit.** Hardcoded strings require finding and replacing every occurrence in the codebase when localizing. Strings in message files require only a new locale file. Retrofit i18n is expensive: text is scattered across components, dynamic strings are concatenated with string interpolation (which ICU handles but concatenation does not), and plural rules are unhandled.

  **MUST use the browser's `Intl` API for formatting dates, numbers, and currencies rather than writing custom formatters.** `Intl.DateTimeFormat`, `Intl.NumberFormat`, and `Intl.RelativeTimeFormat` produce locale-correct formatted strings without a dependency on a formatting library. Custom formatters produce incorrect output for non-English locales and require maintenance as locale conventions change.

  **SHOULD choose a library that supports ICU message format rather than simple string interpolation.** Simple interpolation — `"Hello, {name}!"` — handles variable substitution but not pluralization, gender selection, or rich formatting. ICU message format handles all of these. Migrating from simple interpolation to ICU after strings are in production requires updating every translated string, which is expensive in all supported languages.

### Task 2: FEE-2001 Message Formatting & ICU Syntax

**Files:**
- Create: `docs/en/Internationalization and Localization/2001.md`

- [ ] **Step 1: Write EN article**

  **Frontmatter:** `id: 2001`, `title: Message Formatting & ICU Syntax`, `state: draft`, `category: Internationalization and Localization`

  **Opening context:** A message string in an internationalized application is not a static string — it is a template that may contain interpolated variables, conditional text based on numeric values, conditional text based on categorical choices, and formatted numbers or dates. ICU message format is the syntax that expresses all of these in a single string that can be translated as a unit. Understanding ICU syntax is the prerequisite for writing strings that translate correctly across all supported languages.

  **`## Design Thinking` subsections:**
  - `### Variable interpolation: {variable}` — The simplest ICU feature. `"Hello, {name}!"` with `{ name: 'Alice' }` produces "Hello, Alice!". The variable name is referenced in translation strings, so translators can reorder variables for language-appropriate word order. Concatenation — `"Hello, " + name + "!"` — cannot be translated because the concatenation order is fixed in code.
  - `### Plural selection: {count, plural, ...}` — `"You have {count, plural, one {# message} other {# messages}}"` selects the correct form based on `count`. The `#` token is replaced by the formatted count. Each language has its own plural categories (zero, one, two, few, many, other) and rules for which numbers fall into each category. ICU handles this per-locale; manual `if count === 1` conditionals do not.
  - `### Select: {gender, select, ...}` — `"{gender, select, male {He} female {She} other {They}} liked your post."` selects text based on a categorical value. This is used for grammatical gender, verb conjugation, and any other categorical string variation. Languages with grammatical gender require this for correct localization.

  **`## Best Practices`:**

  **MUST use ICU variable placeholders instead of string concatenation for any string that contains dynamic values.** `"Welcome back, " + username` cannot be properly translated — the translator receives the static parts as separate strings and cannot adjust word order. `"Welcome back, {username}"` is translated as a single unit where the translator can place `{username}` at the grammatically correct position.

  **MUST use ICU plural syntax for any string that changes based on a count.** An `if count === 1` conditional in code is a hardcoded English plural rule. Russian, Polish, Arabic, and many other languages have more than two plural forms. ICU's `{count, plural, ...}` syntax with all applicable categories delegates plural selection to the i18n library's locale-aware rules.

  **SHOULD include all relevant plural categories for a message, even if the English translation treats some categories identically.** For English, `one` and `other` are sufficient. For languages with `zero`, `few`, and `many` categories, translators need these slots. If a message uses only `one` and `other`, translators for languages with additional categories cannot provide correct translations.

### Task 3: FEE-2002 Pluralization & Gender Rules

**Files:**
- Create: `docs/en/Internationalization and Localization/2002.md`
- Create: `docs/zh-tw/Internationalization and Localization/2002.md`

- [ ] **Step 1: Write EN article**

  **Frontmatter:** `id: 2002`, `title: Pluralization & Gender Rules`, `state: draft`, `category: Internationalization and Localization`

  **Opening context:** English has two plural forms: singular (1 item) and plural (0 items, 2 items, 100 items). This simplicity is the exception. Arabic has six plural forms. Russian has four. Welsh has six. Polish has four. The CLDR (Common Locale Data Repository) defines the plural categories for every language and the rules for which numbers fall into each category. i18n libraries that support CLDR plural rules select the correct category automatically; implementations that hardcode `if count === 1` produce wrong output in every language but English.

  **`## Design Thinking` subsections:**
  - `### CLDR plural categories` — The CLDR defines six plural categories: `zero`, `one`, `two`, `few`, `many`, `other`. Not all languages use all categories. English uses `one` and `other`. Arabic uses all six. The rules are mathematical: in Russian, numbers ending in 1 (except 11) use `one`; numbers ending in 2–4 (except 12–14) use `few`; all others use `many` or `other`. These rules are encoded in i18n libraries — they should not be reimplemented.
  - `### Ordinal vs. cardinal plurals` — Cardinal plurals count items (1 cat, 2 cats). Ordinal plurals express rank (1st, 2nd, 3rd). ICU supports both with `{n, plural, ...}` (cardinal) and `{n, selectordinal, ...}` (ordinal). English ordinals have four forms: one (1st), two (2nd), few (3rd), other (4th and above). Other languages have different ordinal systems.
  - `### Gender and grammatical agreement` — Languages with grammatical gender require verbs, adjectives, and articles to agree with the noun's gender. In Spanish, "the user submitted a new document" uses different articles and adjective endings depending on whether the user's grammatical gender is masculine or feminine. ICU's `select` format handles this: `{gender, select, masculine {...} feminine {...} other {...}}`.

  **`## Best Practices`:**

  **MUST use a library with CLDR plural rules for any application that will be localized into languages other than English.** CLDR plural rules are complex, language-specific, and maintained by the Unicode Consortium. Reimplementing them is a maintenance burden that will be incorrect for many languages. i18next, FormatJS, and the browser's `Intl.PluralRules` API implement CLDR rules correctly.

  **MUST provide translation slots for all CLDR plural categories that a language uses, not just `one` and `other`.** When translation files contain only `one` and `other`, translators for languages with `few`, `many`, or `zero` categories cannot provide correct translations. The source file (English) should include `zero`, `one`, `two`, `few`, `many`, and `other` as keys, even if the English values for multiple categories are identical. Translators will provide language-specific values.

  **SHOULD use `Intl.PluralRules` to select plural categories when implementing custom formatting outside of an i18n library.** `new Intl.PluralRules('ru').select(21)` returns `'one'` (the Russian rule: 21 ends in 1, not 11). This is the browser-native implementation of CLDR rules and requires no library dependency.

### Task 4: FEE-2003 Date, Number & Currency Formatting

**Files:**
- Create: `docs/en/Internationalization and Localization/2003.md`
- Create: `docs/zh-tw/Internationalization and Localization/2003.md`

- [ ] **Step 1: Write EN article**

  **Frontmatter:** `id: 2003`, `title: Date, Number & Currency Formatting`, `state: draft`, `category: Internationalization and Localization`

  **Opening context:** Numbers, dates, and currencies have locale-specific formatting conventions that differ fundamentally across regions. The decimal separator is a period in en-US and a comma in de-DE. Dates are MM/DD/YYYY in en-US and DD/MM/YYYY in en-GB. Currency symbols precede the amount in en-US and follow it in some European locales. The browser's `Intl` API handles all of these correctly without a dependency, using the same CLDR data that underpins every other i18n implementation.

  **`## Design Thinking` subsections:**
  - `### Intl.DateTimeFormat` — `new Intl.DateTimeFormat('de-DE', { dateStyle: 'long' }).format(date)` formats a date as "13. April 2026" in German conventions. Options include `dateStyle`, `timeStyle`, `timeZone`, and individual fields (`year`, `month`, `day`, `hour`, `minute`). The `timeZone` option is critical: a date object in UTC formatted without a timezone will display the UTC time, not the user's local time.
  - `### Intl.NumberFormat` — `new Intl.NumberFormat('de-DE').format(1234.56)` produces "1.234,56". Options include `style: 'currency'` with a `currency` code, `style: 'percent'`, `maximumFractionDigits`, and `notation: 'compact'` for abbreviations (1K, 1M). Currency formatting (`style: 'currency', currency: 'EUR'`) produces the correct symbol, placement, and decimal convention for the locale.
  - `### Relative time: Intl.RelativeTimeFormat` — `new Intl.RelativeTimeFormat('en', { numeric: 'auto' }).format(-1, 'day')` produces "yesterday". `format(-3, 'day')` produces "3 days ago". This is the correct way to produce locale-aware relative time strings — not a custom "X minutes ago" function that hardcodes English grammar.

  **`## Best Practices`:**

  **MUST use `Intl.DateTimeFormat`, `Intl.NumberFormat`, and `Intl.RelativeTimeFormat` for locale-aware formatting rather than custom formatters or date libraries without locale support.** The `Intl` API is a browser built-in with no dependency cost, uses CLDR data maintained by the Unicode Consortium, and supports all standard locale conventions. Custom formatters or libraries that produce formatted strings without locale awareness produce incorrect output for non-English locales.

  **MUST always pass an explicit `timeZone` option when formatting dates with `Intl.DateTimeFormat`.** Without a `timeZone`, formatting uses the environment's default timezone, which may be the server's timezone (UTC) in SSR contexts or may differ from the user's timezone. Pass `timeZone: userTimezone` where `userTimezone` is obtained from `Intl.DateTimeFormat().resolvedOptions().timeZone` (the browser's detected timezone) or from user preferences.

  **SHOULD memoize `Intl` formatter instances rather than creating a new instance on every render.** `new Intl.DateTimeFormat()` is an object construction call with a non-trivial cost. In a component that formats dates on every render, creating a new formatter each time accumulates cost. Cache the formatter instance outside the render function or in a `useMemo` call.

### Task 5: FEE-2004 RTL Layout & Bidirectional Text

**Files:**
- Create: `docs/en/Internationalization and Localization/2004.md`
- Create: `docs/zh-tw/Internationalization and Localization/2004.md`

- [ ] **Step 1: Write EN article**

  **Frontmatter:** `id: 2004`, `title: RTL Layout & Bidirectional Text`, `state: draft`, `category: Internationalization and Localization`

  **Opening context:** Arabic, Hebrew, Persian, and Urdu are written right-to-left (RTL). A layout built for LTR languages mirrors horizontally for RTL: the navigation that is on the left in English appears on the right in Arabic; the progress bar that fills left-to-right in English fills right-to-left in Arabic; a button that has an icon on the left has the icon on the right in RTL. Achieving this mirror automatically requires using CSS logical properties and the `dir` attribute rather than physical directional properties.

  **`## Design Thinking` subsections:**
  - `### CSS logical properties: the right abstraction` — CSS physical properties name directions absolutely: `margin-left`, `padding-right`, `border-left`. CSS logical properties name directions relative to writing mode: `margin-inline-start`, `padding-inline-end`, `border-inline-start`. In LTR, `inline-start` is left; in RTL, `inline-start` is right. Replacing physical properties with logical properties makes the layout mirror automatically when `dir="rtl"` is set.
  - `### The dir attribute and language tags` — Setting `dir="rtl"` on the `<html>` element enables the browser's bidirectional text algorithm and flips CSS logical properties. The `lang` attribute on `<html>` (e.g., `lang="ar"`) enables locale-specific rendering for text shaping, quotation marks, and hyphenation. Both attributes should be set together for RTL locales.
  - `### Bidirectional text: mixed LTR and RTL` — A page in Arabic that contains an English URL or a code snippet contains mixed-direction text. The Unicode Bidirectional Algorithm handles most cases automatically. For cases that require explicit control, the `<bdo>` element and the `unicode-bidi` CSS property force text direction for a specific span.

  **`## Best Practices`:**

  **MUST use CSS logical properties (`inline-start`, `inline-end`, `block-start`, `block-end`) instead of physical directional properties (`left`, `right`, `top`, `bottom`) for all layout properties that should mirror in RTL.** Physical properties are absolute; logical properties are relative to writing direction. A component styled with `margin-left` will not mirror in RTL; a component styled with `margin-inline-start` will mirror automatically when `dir="rtl"` is set on an ancestor element.

  **MUST set both `dir` and `lang` attributes on the `<html>` element when rendering an RTL locale.** `dir="rtl"` enables directional layout mirroring via CSS logical properties and the browser's bidirectional text algorithm. `lang="ar"` (or the appropriate language code) enables locale-specific text rendering. Both are required together: `dir` handles layout; `lang` handles typography and shaping.

  **SHOULD test RTL layout by setting `dir="rtl"` on the root element in development rather than waiting until a right-to-left locale is added.** Testing RTL early catches physical-property usage that would need to be replaced. A useful development practice: add a keyboard shortcut or a `?rtl=true` query param that adds `dir="rtl"` to `<html>` for any component in development.

### Task 6: FEE-2005 Locale Detection & Routing

**Files:**
- Create: `docs/en/Internationalization and Localization/2005.md`
- Create: `docs/zh-tw/Internationalization and Localization/2005.md`

- [ ] **Step 1: Write EN article**

  **Frontmatter:** `id: 2005`, `title: Locale Detection & Routing`, `state: draft`, `category: Internationalization and Localization`

  **Opening context:** Before a localized application can show the correct language, it must determine the user's preferred locale. Three sources are available: the `Accept-Language` HTTP header (set by the browser), the URL (path prefix `/en/` or subdomain `fr.example.com`), and a user preference stored in a cookie or account settings. The URL is the most reliable and SEO-friendly source — it makes the locale explicit and cacheable. The `Accept-Language` header is the most automatic source but requires server-side reading.

  **`## Design Thinking` subsections:**
  - `### URL-based locale: path prefix vs. subdomain` — Path prefix (`/en/page`, `/fr/page`) is easier to implement and keeps all content on the same domain, which is better for link equity. Subdomain (`en.example.com`, `fr.example.com`) is a valid alternative and may be preferred for content that is substantially different across locales. Path prefix is the more common choice for applications; subdomain is more common for multi-locale content sites.
  - `### Locale negotiation` — When the user's preferred locale is `fr-CA` (French Canadian) and the application supports `fr` and `en`, the application should fall back to `fr` before `en`. This negotiation — matching the most specific supported locale to the user's preference — is locale matching. The `Intl.LocaleMatcher` proposal (or the `@formatjs/intl-localematcher` polyfill) implements this correctly.
  - `### Redirect vs. serve on detection` — When a user arrives at `/` without a locale prefix, the application can either redirect to `/en/` (redirect) or serve the localized content at `/` (serve). Redirect is simpler and allows search engines to index locale-specific URLs. The redirect should be a 302 (temporary) for locale negotiation, not 301 (permanent), so the redirect is re-evaluated if the user's preferences change.

  **`## Best Practices`:**

  **MUST use URL-based locale routing (path prefix or subdomain) as the primary locale signal for publicly accessible content.** URL-based locale is explicit, cacheable by CDNs, indexable by search engines with correct `hreflang` annotations, and shareable — a user can share a URL in their language and the recipient receives the same language. Cookie-based or header-based locale produces URLs that resolve to different content for different users, preventing caching and correct SEO.

  **MUST include `hreflang` link elements in the `<head>` for every supported locale of a page.** Search engines use `hreflang` to understand that `/en/about` and `/fr/about` are the same page in different languages. Missing `hreflang` causes search engines to treat locale variants as duplicate content, which can suppress rankings for non-English locales.

  **SHOULD implement locale fallback with a proper locale negotiation algorithm rather than exact locale matching.** A user with `navigator.language === 'fr-CA'` should receive French content if `fr-CA` is not available but `fr` is. Exact matching (`supportedLocales.includes(userLocale)`) misses this fallback and shows the default locale to users whose region-specific locale is not supported.

  **Frontmatter:** `id: 2006`, `title: Translation Workflow & String Extraction`, `state: draft`, `category: Internationalization and Localization`

  **Opening context:** A translation workflow is the process by which strings move from code to translators and back into the application. Without a defined workflow, translation is ad-hoc: strings are extracted manually, sent as spreadsheets, returned with errors, and reintegrated manually. An automated workflow — extract strings from code, sync to a TMS (Translation Management System), receive translations, and deliver them as locale files — scales to any number of languages and integrates with the development process rather than interrupting it.

  **`## Design Thinking` subsections:**
  - `### String extraction: i18next-parser` — i18next-parser scans source files for calls to `t('key')` and `useTranslation()` and generates message files with all discovered keys. It handles nested keys, namespaces, and plural keys. Running the parser in CI ensures that new strings are extracted before a release and that the translation files are complete.
  - `### Key naming conventions` — Keys can be semantic (`user.profile.title`) or content-based (`"Welcome to your profile"`). Semantic keys require translators to understand context from the key name; content-based keys are self-documenting but change when the English text changes (breaking the mapping to existing translations). Semantic keys with a `context` description in the translation file are the better default for applications with many strings.
  - `### TMS integration: Crowdin, Phrase, Lokalise` — A TMS stores translation memory (previously translated strings), manages translation projects, provides a web interface for translators, and can integrate with GitHub via webhooks to automatically sync locale files. Connecting the TMS to the repository via CI — extract → push to TMS → pull translations → commit — removes manual steps from the workflow.

  **`## Best Practices`:**

  **MUST run string extraction as part of the CI pipeline and fail the build if untranslated keys are present in a release build.** Manual extraction is forgotten. CI extraction ensures that every new string is accounted for before release. A build check that counts untranslated keys and fails above a threshold (or fails for any untranslated key in critical paths) enforces completeness.

  **MUST provide context descriptions for translation keys that are not self-explanatory from their value alone.** A key with value "View" could mean "to view something" (verb) or "a view" (noun). In German, these translate to different words. Context descriptions — stored as `_comment` keys in most i18n formats — give translators the grammatical and contextual information they need to produce correct translations.

  **SHOULD use namespaces to group related strings and load only the namespaces needed for the current route.** A single large translation file loaded on every page is inefficient for large applications. i18next supports namespaces as separate files (`common.json`, `checkout.json`, `dashboard.json`). Loading only the namespaces for the current page reduces the translation bundle size for users who never visit certain routes.

  **Frontmatter:** `id: 2007`, `title: i18n in Component Libraries`, `state: draft`, `category: Internationalization and Localization`

  **Opening context:** A component library that ships hardcoded English strings in its components — "Close", "Previous", "Next", "Loading", "No results found" — is not usable in non-English products without forking the library. Internationalizing a component library requires exposing these strings as props or via a locale context, providing default English values, and documenting the override mechanism for consumers. For design system teams, this is a first-class concern that is easier to address at library creation than retrofit later.

  **`## Design Thinking` subsections:**
  - `### String injection patterns: props vs. context` — Passing translation strings as props to every component that uses them is explicit but creates prop bloat: a `<DataTable>` with pagination, search, and filtering has a dozen system strings. A locale context that maps string keys to translated values allows components to look up strings without prop threading. The two patterns are complementary: props for high-visibility strings that consumers commonly customize; context for system strings that are correct for the locale and rarely changed.
  - `### Locale-aware formatting in components` — Components that display dates, times, relative time, or numbers must use `Intl` API with the current locale, not hardcoded formatting. A `<RelativeTime value={date} />` component should accept a `locale` prop or read it from context and use `Intl.RelativeTimeFormat` to produce the correct output.
  - `### RTL support in component layout` — Components that have directional layout — sidebars, breadcrumbs, navigation arrows, progress bars — must use CSS logical properties (see FEE-2004) to mirror correctly in RTL. A component library that uses physical properties (`margin-left`, `float: right`) throughout will require per-component fixes when RTL support is requested.

  **`## Best Practices`:**

  **MUST expose all user-visible system strings in components as overridable via props or a locale context rather than hardcoding them.** Hardcoded system strings are invisible in the component's API documentation and require forking the library or wrapping every component to override. A locale context with default English values and a documented override mechanism makes the strings visible, overridable, and i18n-ready without any additional work for English-only consumers.

  **MUST use CSS logical properties for all directional layout in component library code.** Physical properties (`margin-left`, `padding-right`) require per-component overrides for RTL support. Logical properties (`margin-inline-start`, `padding-inline-end`) mirror automatically. A component library that ships with logical properties throughout provides RTL support to consumers at no additional cost.

  **SHOULD provide a locale-aware formatting context that components can use to format dates and numbers rather than accepting formatted strings as props.** Accepting pre-formatted strings as props transfers the formatting responsibility to the consumer, who must know to use `Intl.DateTimeFormat` with the correct locale. A `LocaleProvider` context that exposes formatting utilities allows components to format correctly for the active locale without consumer-side formatting logic.
